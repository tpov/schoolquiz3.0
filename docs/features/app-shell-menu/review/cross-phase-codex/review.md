1. `blocker` [MainActivity](/home/Programming/Android/schoolquiz4.0/apps/android-next/src/main/java/com/tpov/schoolquiz/apps/android_next/MainActivity.kt:28), [MainActivity](/home/Programming/Android/schoolquiz4.0/apps/android-next/src/main/java/com/tpov/schoolquiz/apps/android_next/MainActivity.kt:55), [DefaultRootComponent](/home/Programming/Android/schoolquiz4.0/android/feature/app-shell/presentation/src/main/kotlin/com/tpov/schoolquiz/android/feature/app_shell/presentation/component/DefaultRootComponent.kt:57), [DefaultRootComponent](/home/Programming/Android/schoolquiz4.0/android/feature/app-shell/presentation/src/main/kotlin/com/tpov/schoolquiz/android/feature/app_shell/presentation/component/DefaultRootComponent.kt:96)  
`MainActivity` ретейнит весь `DefaultRootComponent` через `componentContext.instanceKeeper.getOrCreate(...)`. Компонент при этом делегирует `ComponentContext`, созданный для старой `Activity`, и регистрирует `BackCallback` в старом `backHandler`. После rotation это даёт очень реальный риск сломанного system back, stale child contexts и утечки уничтоженной `Activity`.  
Fix suggestion: не хранить весь root в `InstanceKeeper`; создавать новый `DefaultRootComponent` на каждый `onCreate()` через `get { parametersOf(defaultComponentContext()) }`, а переживающую rotation логику держать только внутри `instanceKeeper` самого компонента. Если нужен retained root, использовать штатный retained-root pattern и отдельно аудировать зависимости на утечки.

2. `blocker` [apps/android-next/build.gradle.kts](/home/Programming/Android/schoolquiz4.0/apps/android-next/build.gradle.kts:1), [AppApplication](/home/Programming/Android/schoolquiz4.0/apps/android-next/src/main/java/com/tpov/schoolquiz/apps/android_next/AppApplication.kt:14), [FirebaseInitializer](/home/Programming/Android/schoolquiz4.0/platform/firebase/src/main/kotlin/com/tpov/schoolquiz/platform/firebase/FirebaseInitializer.kt:8), [FirebaseModule](/home/Programming/Android/schoolquiz4.0/platform/firebase/src/main/kotlin/com/tpov/schoolquiz/platform/firebase/di/FirebaseModule.kt:9)  
Production path до Firebase compile-wired, но не выглядит runtime-wired: app-модуль не применяет `com.google.gms.google-services`, а в текущем дереве нет `google-services.json`/эквивалентных `google_app_id` ресурсов для `com.tpov.schoolquiz.next`. При этом `AppApplication` всегда вызывает Firebase init, а `firebaseModule` лениво создаёт `FirebaseFirestore.getInstance()` и `FirebaseAuth.getInstance()`. Fix suggestion: либо подключить `google-services` plugin и конфиг для `apps/android-next`, либо инициализировать `FirebaseApp` через явный `FirebaseOptions`. До этого не полагаться на `firebaseModule` как на рабочий production adapter.

3. `high` [DefaultRootComponent](/home/Programming/Android/schoolquiz4.0/android/feature/app-shell/presentation/src/main/kotlin/com/tpov/schoolquiz/android/feature/app_shell/presentation/component/DefaultRootComponent.kt:102), [AppShellState](/home/Programming/Android/schoolquiz4.0/shared/feature/app-shell/domain/src/commonMain/kotlin/com/tpov/schoolquiz/shared/feature/app_shell/domain/state/AppShellState.kt:59)  
Есть race между `initUseCase()` и `observeUseCase()`. Если stats observer успевает эмитнуть реального пользователя раньше, чем завершится `initUseCase()`, то `_appShellState` уже перестаёт быть `fallback(guest())`, и init-path сохраняет guest-derived navigation вместо `AppShellState.default(actualStats)`. Практический эффект: user с `currentSkill >= 3000` может холодно стартовать не в `Arena`, а в `Qualifications`, несмотря на формулу `defaultSection`.  
Fix suggestion: не запускать stats observation до завершения initial state, либо хранить отдельный флаг “user navigation already happened” вместо сравнения всего state c `fallback(guest())`.

4. `high` [AppShellScreen](/home/Programming/Android/schoolquiz4.0/android/feature/app-shell/presentation/src/main/kotlin/com/tpov/schoolquiz/android/feature/app_shell/presentation/ui/AppShellScreen.kt:90), [AppShellScreen](/home/Programming/Android/schoolquiz4.0/android/feature/app-shell/presentation/src/main/kotlin/com/tpov/schoolquiz/android/feature/app_shell/presentation/ui/AppShellScreen.kt:101), [AppShellScreen](/home/Programming/Android/schoolquiz4.0/android/feature/app-shell/presentation/src/main/kotlin/com/tpov/schoolquiz/android/feature/app_shell/presentation/ui/AppShellScreen.kt:129)  
UI↔domain синхронизация drawer сломана на двух уровнях. Во-первых, `LaunchedEffect(Unit)` сравнивает `drawerState.currentValue` с `state.isDrawerOpen`, но `state` здесь долгоживущий captured snapshot, а не гарантированно актуальное значение. Во-вторых, hamburger открывает drawer напрямую через `drawerState.open()`, а не через `navigator.goTo(OpenDrawer)`, то есть domain узнаёт об открытии постфактум. Это создаёт реальный desync: scrim/gesture close может не попасть в domain, а back во время open-animation может пройти не по ветке “close drawer”, а по следующему шагу FSM.  
Fix suggestion: сделать domain single source of truth для drawer. UI intent должен сразу диспатчить `OpenDrawer/CloseDrawer`; domain→UI effect только отражает state. Если оставлять обратную синхронизацию, нужен `rememberUpdatedState` или корректный key вместо `LaunchedEffect(Unit)`.
