# Проверка на устройствах: что нельзя проверить эмулятором

## Зачем этот документ

Ролевая матрица — девять типов аккаунтов на два с лишним десятка сценариев — проверяется автоматически и за секунды:

```
firebase emulators:exec --only auth,firestore "node scripts/rules-emulator-test.js"
```
```
firebase emulators:exec --only auth,firestore,functions "node scripts/review-pipeline-e2e.js"
```

Руками эту матрицу повторяемо не прогнать, и после каждой правки всё пришлось бы начинать заново. Поэтому на устройствах проверяется **только то, чего эмулятор не воспроизводит**: настоящий сетевой стек, настоящие часы, настоящий жизненный цикл процесса и настоящая установка поверх уже стоящего приложения.

Хватит трёх-четырёх телефонов. Больше нужно, только если специально ищешь состязание за общие данные.

## Подготовка

Эмулятору Firestore нужна Java 21+, а Gradle в проекте собирает под 17. Поэтому Java подставляется только команде эмулятора, а не глобально:

```bash
JAVA_HOME=/Library/Java/JavaVirtualMachines/zulu-24.jdk/Contents/Home firebase emulators:start
```

Роли устройств: **A** — автор, **B** — ревьюер (тестер или админ), **C** — посторонний игрок. Четвёртое, если есть, — второй вход в аккаунт A.

Список подключённых устройств и адресация конкретного:

```bash
adb devices -l
```

Дальше везде `adb -s <serial>`.

## 1. Настоящий оффлайн

Эмулятор не воспроизводит ни поведение сетевого стека Android, ни очередь Firestore при обрыве. Проверяется накопление outbox и досылка.

На устройстве C отключить сеть:

```bash
adb -s <serial> shell svc wifi disable && adb -s <serial> shell svc data disable
```

Пройти три-четыре урока подряд. Приложение должно работать полностью: вопросы, таймер, результат, списание жизней по локальному счёту.

Вернуть сеть:

```bash
adb -s <serial> shell svc wifi enable && adb -s <serial> shell svc data enable
```

**Что должно произойти.** Все попытки уезжают на сервер, ни одна не теряется и ни одна не задваивается. Награда начисляется ровно один раз на попытку — за это отвечает `stableId`, и повтор проверен автоматически, но здесь проверяется реальная досылка после разрыва.

**Где смотреть.** Локальная очередь — таблица outbox; серверная сторона — начисления в профиле.

## 2. Расхождение часов

`eventBucketId` больше не зависит от даты клиента — раньше зависел, и одно и то же событие могло попасть в два ведра при разошедшихся часах. Это проверка, что отвязали действительно.

Отключить автоматическое время на устройстве и сдвинуть дату на сутки вперёд, затем на двое назад. В каждом положении пройти урок и синхронизироваться.

**Что должно произойти.** Попытки ложатся в ведро по серверному времени, турнирная таблица не разъезжается, задвоений нет.

## 3. Убийство процесса посреди синхронизации

Сохранение попытки идёт одной транзакцией: сама попытка, её ответы, состояние повторений и строка outbox. Проверяется, что транзакция держится.

Начать урок, дойти до последнего вопроса, ответить и сразу убить процесс:

```bash
adb -s <serial> shell am force-stop com.tpov.schoolquiz
```

**Что должно произойти.** После перезапуска либо попытка сохранена целиком и стоит в очереди на отправку, либо её нет вовсе. Промежуточного состояния — попытка есть, а в очереди её нет — быть не должно.

## 4. Один аккаунт на двух устройствах

Войти одним аккаунтом на A и на четвёртом устройстве. На обоих пройти разные уроки в оффлайне, затем включить сеть сначала на одном, потом на другом.

**Что должно произойти.** Оба набора результатов доходят. Жизни считает сервер, поэтому суммарный расход не должен превышать доступный запас — второе устройство не должно «оплатить» попытки повторно из своего локального представления.

## 5. Ревью между устройствами

Живая проверка того же, что автоматика проверяет на эмуляторе, но через настоящий интерфейс.

На A создать квест и отправить на проверку. На B (тестер) — очередь должна показать задачу **проверки содержания**. Сдать её. Задача логики на B появиться не должна: этапы идут по очереди и логика — право админа.

Переключить B на админа, сдать логику. На C квест должен появиться после синхронизации каталога.

**На что смотреть отдельно.** У модератора очередь пуста — это правильно, его права относятся к чату, а не к ревью.

## 6. Установка поверх legacy

**Самое рискованное и проверяемое только на устройстве.** `applicationId` теперь совпадает с опубликованным — `com.tpov.schoolquiz`. Значит новая сборка встаёт поверх старой у настоящих пользователей.

На устройство со стоящим релизным приложением поставить новую сборку без удаления старой:

```bash
adb -s <serial> install -r app-debug.apk
```

**Что проверить.** Установка не падает по несовпадению подписи. Приложение запускается. Локальная база схлопнута до версии 1, поэтому прежние локальные данные ожидаемо не переносятся — важно, что приложение при этом не падает, а начинает с чистой базы и подтягивает своё с сервера.

Если установка отваливается по подписи — это ожидаемо для отладочной сборки, и проверять надо сборкой, подписанной тем же ключом, что и релиз.

## 7. Снятие логов

```bash
adb -s <serial> logcat -c && adb -s <serial> logcat | grep -iE "schoolquiz|firestore|sync"
```

## Что проверять НЕ надо руками

Всё перечисленное уже покрыто и падает само, если сломается:

- права всех девяти ролей на всех коллекциях — `scripts/rules-emulator-test.js`;
- маршрутизация задач ревью, порядок этапов, разрыв уровней у переводчиков, публикация — `scripts/review-pipeline-e2e.js`;
- пересчёт результата, подделка процента, повторная отправка, исчерпание жизней — там же;
- турнирные группы и таблица — `scripts/tournament-emulator-e2e.js`.
