# ADR-0007: Сертификаты

## Status
Accepted — 2026-04-16; amended — 2026-09-30.

Уточнение текущего MVP: [EXAM AD-19/24](../../_bmad-output/planning-artifacts/architecture/architecture-schoolquiz3.0-2026-08-29/ARCHITECTURE-SPINE.md) и [общий AD-1/16](../../_bmad-output/planning-artifacts/architecture/architecture-schoolquiz3.0-2026-09-29/ARCHITECTURE-SPINE.md) закрепляют exam как владельца выдачи и неизменность выданного свидетельства при ошибке нашего контента.

## Context

В отличие от квалификаций (игровых ролей, см. ADR-0006), **сертификат** — это официальный документ, который юзер может использовать **вне приложения**: в резюме, в реальных работах, при сотрудничестве с работодателями или партнёрами. Сертификат подтверждает, что юзер сдал экзамен по конкретному курсу с определённой оценкой.

Ключевые отличия от квалификаций:

- Сертификат — **реальный документ**, а не игровая штука.
- Верифицируется **третьими сторонами** (работодатель может проверить подлинность сертификата по QR-коду или URL).
- Не даёт игровых прав внутри приложения.
- Выдаётся только за прохождение экзамена по курсу (не за REGULAR-квесты, не за квалификационные собесы).

## Decision

### Единица выдачи — одна успешная попытка по одному курсу

Каждый сертификат соответствует одному `Quest` с `QuestType = COURSE`. Каждая новая успешная попытка итогового экзамена выдаёт отдельный сертификат; повторный запрос по той же попытке возвращает ту же выдачу. Пересдавать можно до и после окончания срока по действующим правилам допуска, цены и cooldown. Провал не создаёт сертификат и не заменяет текущий. Если последующий пересчёт исправляет прежний провал на проходной результат, сертификат за эту старую попытку не выдаётся: для него нужна новая успешная сдача. Уже заработанное при исходном успешном завершении право на выдачу, включая ожидающую подпись, сохраняется.

По умолчанию отображается последний заработанный сертификат, даже если его проходной балл ниже прежнего. Сервер фиксирует порядок earning outcomes; лучший балл и время завершения подписи не определяют текущую выдачу. Более старая подпись, завершившаяся позже, не вытесняет новую. Предыдущие сертификаты остаются неизменными в истории и доступны по своим идентификаторам; каждый сохраняет собственный годовой срок от соответствующей успешной сдачи.

Композитные сертификаты («пакет курсов = один сертификат специализации») **не поддерживаются** в первой итерации. Если понадобятся позже — добавится отдельная сущность `CertificatePath`, без ломки текущей модели.

### Модель

Сертификат — это данные, достаточные для верификации третьей стороной:

```kotlin
data class Certificate(
    val id: CertificateId,
    val userId: UserId,
    val courseId: QuestId,             // ссылка на COURSE-квест
    val score: Score,                  // набранная оценка (звёзды / баллы — уточняется)
    val issuedAt: Instant,
    val serverSignature: String,       // криптоподпись сервера, валидируется при верификации
    val verificationUrl: String,       // публичный URL (например, https://schoolquiz.app/cert/<id>)
)
```

Конкретная форма `Score` и алгоритм подписи — отдельные вопросы реализации, не архитектурные.

### Место жизни

- **Выдача, подпись, проверка и authoritative запись** — у exam через серверный контракт. Для каждой успешной попытки final, включая повторную выдачу, terminal result, неизменяемый факт выдачи и durable задача подписи/публикации фиксируются одной транзакцией. Факт связывает отдельную issuanceId этой sitting, resultVersion, claims, исходные даты, keyId и серверный порядок заработанного результата; подпись выполняется вне транзакции. Pending последней выдачи показывается явно; повтор по той же попытке не создаёт новый сертификат, не пересматривает право из-за более позднего пересчёта и не сдвигает даты.
- **Profile** — read-only проекция списка сертификатов и UI. Существующие profile/domain и profile/data могут обслуживать отображение и разрешённый cache, но не создают и не меняют серверное свидетельство.
- **UI** — два экрана в `android:feature:internet:profile:presentation`:
  1. Список сертификатов юзера (в его профиле).
  2. **Экран верификации** — принимает URL/QR и запрашивает сервер, возвращает статус (valid / invalid / revoked) + исходные данные сертификата. Этот экран доступен **без авторизации**, чтобы третьи стороны могли проверить сертификат без аккаунта.
- **Серверная верификация** — endpoint в `server/functions` (например, `GET /certificates/<id>/verify`). Отвечает валидностью + данными для отображения.
- **Выдача сертификата** — успешный terminal result итогового экзамена → exam фиксирует идемпотентное свидетельство и подпись → разрешённая проекция через sync. Прежняя схема generic client `QuestCompleted` / rewards и `CompletionEffect.IssueCourseCertificate` не является источником права на сертификат; её возможный adapter только читает подтверждённый exam outcome.

### Независимость от квалификаций

**Сертификат никак не связан с `UserQualifications`** (ADR-0006):

- Получение сертификата не требует квалификации.
- Наличие квалификации не даёт сертификат.
- Сертификат не повышает и не понижает квалификацию.

Если в будущем понадобится связь (например, «для повышения TRANSLATOR до 500 нужен сертификат курса "Advanced English"»), она будет добавлена в `qualification:domain` как **read-only ссылка** на `CertificateId`, без прав изменения.

### Отзыв сертификата

Сертификат может быть помечен как **revoked** администратором (если, например, обнаружено мошенничество). Для верификатора это видимо через endpoint `/verify` (возвращает status = revoked). Для юзера — сертификат остаётся в списке, но помечен как отозванный.

## Consequences

### Плюсы
- Сертификат — понятный артефакт с внешней значимостью. Мотивирует юзеров проходить курсы.
- Независимость от квалификаций — чистая модель, никаких cross-coupling. Можно развивать сертификаты как фичу отдельно от игровых ролей.
- Верификация без авторизации — важная фича для работодателей.
- Серверная подпись — защита от подделки. Юзер не может создать себе сертификат клиентом.

### Минусы
- Требуется криптография (подпись/верификация) на сервере — уже не банальный CRUD.
- Один сертификат относится к одному курсу; история повторных выдач не покрывает кейс «хочу один сертификат за пакет курсов». Осознанный долг.
- Публичный endpoint верификации = публичное раскрытие структуры сертификата. Надо внимательно к PII (имя юзера, оценка — ОК; контакты/email — нет).

### Правила
1. Клиент **никогда** не создаёт `Certificate` локально. Только exam на сервере по подтверждённому успешному terminal result итогового экзамена.
2. Верификация — всегда через сервер. Клиент не валидирует подпись сам.
3. Поле `serverSignature` — opaque для клиента, используется только в запросах к серверу.
4. Сертификат не удаляется. Административный revoked имеет отдельное основание. Понижение результата из-за подтверждённой ошибки нашего вопроса сохраняет выданный сертификат без изменений: ID, подписанные claims/score, даты, исходный годовой срок и действительность. Исправленный результат хранится отдельно; срок не продлевается.

5. Выбор последнего сертификата не меняет правило best-result для сданных контрольных тем. Новая выдача не переписывает старые свидетельства и не продлевает их срок.

## Notes

Расположение profile UI/read-model не определяет владельца серверного факта. Точный model/storage seed сверяется с кодом при реализации; публичная проекция замораживает разрешённые данные при выдаче и не читает изменяемые profile/course поля. Ключ подписи имеет идентификатор; материал проверки старых подписей сохраняется при ротации. Сертификат подтверждает сдачу аккаунтом; проверки личности, прокторинга или аккредитации это решение не добавляет.
