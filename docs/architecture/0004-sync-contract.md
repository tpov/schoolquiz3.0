# ADR-0004: Sync-контракт между клиентом и сервером

## Context

В legacy синхронизация была client-driven: одна 8-этапная цепочка в `SyncInteractor` (см. `SyncStage`),
запуск через `WorkManager.OneTimeWorkRequest` на старте, блокировка сервера `lockServer(event)` с
10 retry × 2 сек.

Три уточнения о легаси, которых не было в первой редакции документа:

- Сравнение структур шло **только по версии** (`remoteVersion > localVersion`,
  `StructureDataUtils.kt:36-39`). Таймстемпы `dataUpdateLocal/Global` участвовали отдельно — в списках
  инфо-изменений (`StructureDataExtention.kt:569`, `:588`). Это два разных механизма, а не один LWW.
- `rollbackStructureData` — пустое тело (`SettingLocalDBUseCase.kt:9-11`), хотя воркер зовёт его в трёх
  ветках обработки ошибок. Откат был декоративным.
- **Загрузка вопросов пользователя на сервер из фонового sync никогда не срабатывала.**
  `updateRemoteQuestion` ходит по `changedListQuestionRemote`, который наполняется единственным местом
  под `if (eventId == QUIZ_BY_USER)` (`StructureDataExtention.kt:209`), а воркер этот event пропускает
  первым же условием цикла (`SyncWorker.kt:100-101`). Легаси был односторонним на практике.

Что изменилось в новой архитектуре:

1. **Много серверной логики** (см. ADR-0005): автопромо полок, обработка `CompletionEffect`, выдача
   сертификатов, серверная защита квалификаций. Синк становится двусторонним.
2. **Полки квестов** (ARENA → TOURNAMENT → HOME) меняются на сервере без участия клиента.
3. **Критические события** (оффер квалификации, новый сертификат) должны прилетать даже когда
   приложение закрыто.
4. Клиент может быть offline — изменения юзера должны долго храниться локально и синкаться при связи.

## Decision

### Основные принципы

1. **Offline-first / write-local-first** **[РАБОТАЕТ]**. Локальные изменения пишутся в Room первым.
   Очередью прикрыто всё, чью цену клиент знает заранее: прохождения уроков, оценки квестов, заявки
   квеста на арену, разблокировка урока, перенос квеста на полку, действие ревьюера, снятие лота с
   продажи. **Исключение по решению, не по недоделке (AD-3):** действия, чью цену или награду сервер
   вычисляет в момент вызова — покупка сердца, покупка и смена ника, покупка лота, покупка логотипа,
   открытие коробки, — остаются синхронными и без сети недоступны, о чём кнопка говорит словами
   (история 5.7). Отложить их значило бы показать игроку цену, которой не будет.
2. **Delta sync** **[РАБОТАЕТ]**. Передаются только изменения, не весь датасет.
3. **Per-entity версионирование** **[ЧАСТИЧНО]**. У каждой сущности свои `version` и `lastModifiedAt`.
   Инкремент делает сервер — одной функцией `functions/entity-version.js` (`nextVersion`,
   `setVersioned`), а не клиент. Охват сверки версий при записи — только дерево квеста при публикации
   (`quest_authoring.SUBMIT_ARENA`, см. «Конфликты»); остальные сущности версию несут, но
   `expected_version` с ними не едет, потому что их пишет либо только сервер, либо один автор с одного
   устройства. `version` двигается **только от изменения содержимого** (AD-12): начисление рейтинга
   её не трогает и ведёт свой `ratingVersion`, иначе чужая оценка обесценивала бы ожидаемую версию автора.
4. **Удаление через отсутствие и флаг** **[РАБОТАЕТ]**. Tombstone-поля `deleted` нет; семантика — ниже.
5. **No hard rollback** **[РАБОТАЕТ]**. Провал sync — повтор, не откат локальной работы юзера.

### Обнаружение серверных изменений: журнал `sync_changes`

Канонический механизм. Сервер ведёт журнал изменённых узлов, клиент читает его с курсором.

**Форма записи** — три поля, `{type, id, changedAtMs}` (`functions/index.js`, `syncChangeDocument`).
Запись не содержит данных узла: она только говорит, какой документ перечитать.

**Схема id — документ на узел, а не запись в лог.** Id формируется из типа и id узла, поэтому новое
изменение того же узла **перезаписывает** предыдущую запись:

| Журнал | Путь | Id документа |
|---|---|---|
| Публичный контент каталога | `catalogs/{catalogId}/sync_changes` | `{type}_{id}` |
| Вопросы урока | `lesson_content/{lessonId}/sync_changes` | `{questionId}` |
| Приватные квесты автора | `private/{ownerUid}/sync_changes` | `{catalogId}_{questId}` |
| Задания на ревью | `admin/review/sync_changes` | `{assignmentId}` |

Из этого следует свойство, на которое опирается вся схема: **размер журнала ограничен числом узлов**.
Он не растёт со временем, сборка мусора ему не нужна, retention к нему неприменим. Любая правка,
которая начнёт формировать id из таймстемпа, превратит журнал в неограниченно растущий лог и сломает
это свойство — так сегодня делают сид-скрипты, и это баг сидов, а не альтернативная схема.

**Права**: `sync_changes` читается всеми, пишется только админом (`firestore.rules`).

**Чтение клиентом** **[РАБОТАЕТ]**:

```
fetchChangedSince(scope, cursor):
  changes = scope.sync_changes WHERE changedAtMs > cursor ORDER BY changedAtMs
  сгруппировать changes по type
  для каждого type: repo.refreshByIds(ids)      // источник истины — сам документ узла
  cursor = max(changes.changedAtMs)              // только после успешного применения
```

Курсор хранится в Room (`SyncStateRepository`), по одному ключу на область:

| Ключ курсора | Область |
|---|---|
| `catalogs` | список каталогов |
| `catalog_sync:{catalogId}` | контент каталога |
| `lesson_content:{lessonId}` | вопросы урока |
| `private_quests:{uid}` | приватные квесты автора |
| `review_assignments:{uid}` | задания на ревью |

Курсор двигается **после** успешного применения: провал `refreshByIds` оставляет курсор на месте, и
следующий проход перечитает тот же набор.

Условие выборки строгое (`> cursor`), а курсор ставится в максимум прочитанного. Публикация пишет
всем узлам один `now` одним батчем, поэтому расщепление одной публикации маловероятно; но две записи
в одну миллисекунду из разных источников — публикация и админ-тул — дали бы пропуск второй без следа.
**[ЧАСТИЧНО]** Курсор — пара `(changedAtMs, docId)` (`SyncCursor` в `shared/core/sync`, AD-31): при
равном времени упорядочивает id документа, поэтому две записи в одну миллисекунду не сливаются.
Тип и сравнение есть; перевод всех четырёх журналов на пару — история 7.3, в работе.

**[РАБОТАЕТ]** Выборка изменений ограничена и продолжаема: страница `SyncChangePage` размером
`SYNC_PAGE_SIZE = 200` с `nextCursor` и `hasMore`; курсор двигается после применения страницы, полная
страница — повод зайти снова. Страница считает и `unreadable` — записи, которые читатель не понял и
пропустил (AD-11): пропуск оставляет след, а не исчезает.

**[РАБОТАЕТ]** Сброс курсора существует как операция: `ForceResync` (AD-30) обнуляет курсоры до
`SyncCursor.BEGINNING` и читает журналы с начала под общими воротами `SyncGate` — сначала сброс, потом
чтение, иначе проход, начавшийся до сброса, дописал бы старый курсор поверх. **Лечит только сторону
чтения**: записи очереди и их уже применённые локальные эффекты (AD-23) не трогаются — они верны
локально, сервер о них ещё не знает.

### Семантика удаления

Поля `deleted` нет. Удаление выражается двумя способами, оба **[РАБОТАЕТ]**:

1. **Сервер не вернул id.** `refreshByIds` запрашивает набор id; всё, чего нет в ответе, удаляется
   локально. Это основной путь.
2. **Пустая видимость.** Квест с пустым `visibleOn` удаляется с устройства даже если документ
   вернулся; флаг `archived` играет ту же роль для остальных типов.

Оба пути работают только потому, что удаление узла сопровождается записью в журнал — иначе клиент
никогда не узнает, что надо перепроверить id.

### Отправка на сервер

**[РАБОТАЕТ]** Очередь одна — таблица `outbox` (`OutboxEntity`, `shared/core/persistence`), три
прежние типизированные таблицы (`lesson_result_attempt_outbox`, `quest_rating_outbox`,
`quest_arena_submission`) сняты миграцией (история 2.9). Ядро в `shared/core/outbox` не знает ни
одной фичи: тело — текст JSON, ссылка на сущность — непрозрачная строка (AD-5, AD-7). Запись:

```
mutation_id        ключ идемпотентности, рождается вместе с намерением и не меняется (AD-2)
owner_uid          чья запись (AD-8)
operation          <фича>.<ИМЯ>, имя владеющей фичи (NFR4)
payload            тело как текст JSON
entity_ref         <фича>.<СУЩНОСТЬ>:<id> — чтобы экран сущности спросил «что с моей записью» (AD-14)
expected_version   версия, с которой мутация уходила; пусто у неверсионируемых
server_version     версия, которую назвал сервер при конфликте
state              ЖДЁТ | ЖДЁТ_ПРЕДУСЛОВИЯ | КОНФЛИКТ | КАРАНТИН | СИНХРОННАЯ
attempt_count, next_retry_at_ms, last_error, created_at_ms
```

Операции (реестр `OutboxOperations`, тот же список на сервере, сверяется тестом
`OutboxOperationsRegistryTest`): `lesson_runner.SUBMIT_ATTEMPT`, `lesson_runner.SUBMIT_RATING`,
`quest_authoring.SUBMIT_ARENA`, `quest_authoring.SUBMIT_REVIEW`, `quest.SET_SHELF`,
`profile.CANCEL_NICKNAME_LISTING`, `profile.CANCEL_LOGO_LISTING`, `UNLOCK_LESSON` (единственная без
префикса фичи — долг, см. `deferred-work.md`).

Транспорт один — callable `submitMutation` в `functions/index.js` (AD-6): проверяет ключ
(`functions/mutation-queue.js`: резерв → выполнение → запись результата), сверяет `expected_version`,
зовёт тело операции по реестру `MUTATION_HANDLERS`. Отказ тела освобождает резерв ключа; тело, чей
эффект не умещается в транзакцию с ключом, получает `mutationId` и выводит из него свой
детерминированный идентификатор (решение ревьюера — `reviewId`). Прямые callable четырёх переехавших
действий на сервере пока живы и ключ обходят — снять после переезда инструментального теста
(`deferred-work.md`).

Прямым вызовом без очереди остаются только действия с серверной ценой (AD-3, п. 1 принципов):
`claimNickname`, `buyLogo`, `applyShopPurchase`, покупка лота, `openGiftBox`.

**[РАБОТАЕТ]** Общий движок повторов `OutboxEngine` / `OutboxPolicy`: экспоненциальный backoff с
потолком; **карантин** после `maxAttempts = 5` окончательных отказов **или** по возрасту записи
старше `queueRecordMaxAgeMs` = 7 дней. Сроки — одно объявление на клиент и сервер,
`config/sync-params.json` (NFR9): предельный возраст записи 7 дней строго меньше срока хранения
ключа `mutationKeyTtlMs` = 30 дней, иначе пережившая возраст запись была бы для сервера новой
операцией (AD-1). Отказ сервера различается по ветви (история 5.1, `SyncError`): `NoNetwork` и
`Unknown` — повтор; `PreconditionNotMet` — ждать предусловие; `Refused` — окончательно;
`VersionConflict` — отдельная ветвь, не отказ (AD-24).

**Карантин терминален и виден (AD-28):** владеющая фича обязана либо откатить локальное изменение,
либо пометить сущность для игрока — молчаливого расхождения не бывает. Пометка читается по
`entity_ref`; новое намерение по той же сущности снимает и карантинную запись прежнего (уточнение
2026-09-02, иначе после доставки нового старая пометка возвращалась).

**[РАБОТАЕТ]** Записи очереди принадлежат создавшему их аккаунту: выборка идёт по `owner_uid`
(история 6.1), под другим `uid` запись не отправляется. Смена аккаунта (AD-8): `AccountSwitchGuard`
сливает очередь **до** `signInWithCredential` и возвращает, сколько осталось; остаток не блокирует
вход, но экран предупреждает словами (`GoogleLinkOutcome.SWITCHED_WITH_UNSENT`). Снятие следов
прежнего владельца (история 6.2) и текст предупреждения (6.4) — в работе.

Идемпотентность **обязательна** для любой операции очереди: повторная доставка не удваивает эффект.

#### Тело записи `SUBMIT_ATTEMPT`

**[РАБОТАЕТ]** Прохождение урока ставится в общую очередь одной транзакцией со строкой прохождения
и строками ответов (`RoomLessonResultOutboxWriter.buildAttemptRow`, `LessonAttemptRepositoryImpl.save`).
Тело собирается целиком в момент намерения (AD-2) и в момент отправки не дочитывается. Поля:

| Поле | Тип | Что это |
|---|---|---|
| `attemptId` | string | ключ идемпотентности; повтор не оплачивается |
| `userId` | string | обязан совпадать с uid вызывающего |
| `scope`, `ownerUid`, `catalogId`, `questId`, `sectionId`, `themeId`, `lessonId`, `sourceShelf` | string, `ownerUid` может быть null | контекст контента; `ownerUid` только для `private` |
| `lessonVersion` | int | версия урока на момент прохождения |
| `difficulty` | `EASY` или `HARD` | |
| `codeAnswer` | string | цифра на позицию пула: `'0'` — не показан, `'1'..'9'` — показан |
| `percentScore` | int | клиентский расчёт; сервер пересчитывает и сверяет |
| `completedAtMs`, `createdAtMs` | int | |
| `answers[]` | `{questionId, codeAnswerIndex, score, answerPayload, answeredAtMs, durationMs, wasTimeout}` | что было выбрано на каждом отвеченном вопросе |
| `served[]` | `{questionId, codeAnswerIndex}` | какие вопросы были сданы в порядок показа (E2.10) |

Правила для `served`:

1. **Отсутствие ключа — «неизвестно», пустой список — «ничего не показано».** Ключ пишется только
   когда список передан. Тела, поставленные до этой редакции, и строки, перенесённые миграцией,
   ключа не несут; сервер обязан отличать это от `[]`.
2. Записи **отсортированы по позиции** и **уникальны** и по позиции, и по `questionId` — клиент
   проверяет это при сборке (`toServedQuestions`), сервер — при чтении (`readServed`).
3. Каждая позиция лежит внутри `codeAnswer`, и каждая строка `answers[]` называет пару
   `(questionId, codeAnswerIndex)`, которая есть в `served`. Писатель отвергает нарушение до
   транзакции: на устройстве это `SaveFailed`, а не карантин недели спустя.
4. **При выходе из урока отправляется весь порядок показа**, а не достигнутая часть:
   `buildCodeAnswerOnAbort` ставит недостигнутым вопросам `'1'`, они считаются показанными, и
   `served` обязан говорить то же. Отправить только достигнутые — уменьшить знаменатель и молча
   завысить процент.
5. Инвариант, который держит всё вместе: **позиции в `served` — ровно те, где цифра `codeAnswer`
   не `'0'`**, на обоих путях.

**[РЕШЕНО]** Сервер сегодня поле отбрасывает: `normalizeLessonResultAttemptEvent` собирает событие
из именованных полей. Шаг подключения (`functions/attempt-scoring.js`, `readServed`) начнёт
расставлять цифры по `served`, а не по слову клиента; тело без ключа станет `served-unknown` и
оплачено не будет.

### Каналы доставки серверных изменений

| Канал | Использование | Статус |
|---|---|---|
| **Pull по журналу** | Весь контент и профиль, по расписанию и вручную | **[РАБОТАЕТ]** — единственный работающий канал |
| **Firestore real-time listeners** | Точечно: статистика игрока, комментарии к уроку | **[ЧАСТИЧНО]** — две точки вне контракта `shared/core/sync`, не общий канал |
| **FCM push** | Три критических события: квест опубликован, рейтинг автора (квалификация) изменился, верификация одобрена | **[РАБОТАЕТ]** — реестр `PUSH_EVENTS` в `functions/push-notifications.js`, клиент `platform/firebase/.../push` |

Push несёт **повод, а не данные** (AD-20): тело сообщения — ровно `eventType`, `entityRef`,
`targetUid`, и ни одно поле приложение не применяет к своим таблицам — получив push, оно поднимает
обычную синхронизацию. Реестр событий на сервере — единственный источник; клиентская копия
сверяется тестом `PushEventsRegistryTest`. Токен устройства лежит в `users/{uid}/devices/{token}`
под текущим аккаунтом, снимается до смены аккаунта и возвращается, если вход не удался; сообщение с
чужим `targetUid` не показывается и просит сервер снять токен. Отправка идёт **после** коммита
операции и никогда не роняет её. Задержка обещаний ADR-0006/ADR-0007 теперь — секунды, а не
плановая синхронизация.

**Push несёт повод, а не данные.** Полезная нагрузка уведомления не является источником истины:
получив push, приложение синхронизируется обычным путём. Это удерживает один механизм применения
изменений вместо двух.

### Расписание и запуск

**[РАБОТАЕТ]**, и в первой редакции документа отсутствовало.

`SyncFrequency`: `MANUAL`, `ON_LAUNCH`, `DAILY`, `EVERY_3_DAYS`, `WEEKLY`. По умолчанию `DAILY`.

Каденций две и они независимы: **контент** (`SyncWorker`) и **профиль** (`ProfileSyncWorker`). Обе
хранятся в `SyncPreferences` по имени enum и перечитываются на каждом `onCreate` — это же перевзводит
периодические воркеры после force-stop и обновления приложения. Ручной запуск доступен всегда, вне
зависимости от каденции.

Порядок syncables задаётся в `apps/android-next/**/di/SyncModule.kt`. Профиль в списке стоит **дважды**
намеренно: второй раз — после отправки результатов, чтобы забрать начисленные сервером награды.

`SyncWorker.performSync` **не fail-fast**: шаги независимы, и упавший профиль не должен оставлять
приложение без контента. Ошибка любого шага даёт `Result.retry()` за весь пакет, поэтому успешные шаги
выполнятся повторно — отсюда требование идемпотентности выше.

**[РАБОТАЕТ]** Профильная каденция запускает профильный воркер (эпик 9): `ON_LAUNCH` профиля ставит
`ProfileSyncWorker`, а не контентный список; выбор `ON_LAUNCH` в любом из двух пикеров запускает
соответствующий воркер сразу; расписание ставит только планировщик, реконсиляция на старте поднимает
воркер той каденции, которая выбрана.

### Разрешение конфликтов

**[РАБОТАЕТ]** Из журнала клиент доверяет серверу безусловно: `refreshByIds` пишет пришедший документ
поверх локального без сравнения версий. Сравнение `version` применяется только на пути обычного
обновления, не из журнала.

**[РАБОТАЕТ]** Серверная валидация вместо доверия клиенту. Поля, защищённые серверно (ADR-0006:
квалификации; ADR-0007: сертификаты; ADR-0005: `CompletionEffect`), игнорируют клиентскую версию —
пишет только сервер.

**[РАБОТАЕТ]** `version` инкрементирует **сервер** (эпик 8): одна функция `functions/entity-version.js`
вместо четырёх мест, клиент `localRevision` больше не шлёт. Приватный и публичный документы квеста
несут одну и ту же серверную версию, клиент никогда не подменяет отсутствующую серверную версию
своей (AD-24).

**[РАБОТАЕТ]** Оптимистичная блокировка — для дерева квеста при публикации
(`quest_authoring.SUBMIT_ARENA`): клиент шлёт `expected_version`, приёмник сверяет с версией
документа и отвечает `ABORTED` с деталью `version-conflict` и `serverVersion`; запись очереди уходит
в состояние КОНФЛИКТ и хранит `server_version`; экран черновика показывает «поверх версии N».
Конфликт — не отказ и не откат: он разрешается **новой мутацией с новым ключом** поверх серверной
версии (AD-24); конфликт без названного числа разрешить нельзя. Расхождение черновика с сервером
после собственной публикации не считается конфликтом: черновик в статусе ожидания ревью принимает
серверную ревизию (`ADOPT_SERVER_REVISION`).

### Схема полей синхронизируемых сущностей

**[РАБОТАЕТ]** — то, что действительно пишется:

```
id: String              // стабильный id узла
version: Long           // назначается клиентом при публикации (см. «Конфликты»)
lastModifiedAt: Long    // Unix millis, серверное время записи
archived: Boolean       // скрытие узла
```

Квест дополнительно несёт `visibleOn: List<String>` (полки) и `authorUid`.

Поля `deleted` и `createdBy` из первой редакции документа не существуют: удаление выражено иначе
(см. «Семантика удаления»), авторство — через `authorUid` там, где оно нужно.

Запись общей очереди — см. «Отправка на сервер».

## Consequences

### Плюсы
- **Журнал дёшев и не растёт.** Документ на узел, чтение с курсором, GC не нужен.
- **Per-entity sync** устраняет главную проблему легаси: сбой на одном шаге не ломает цепочку.
- **Прохождения и оценки не теряются** без сети и не удваиваются при повторе.
- **Расписание в руках игрока**, при этом ручной запуск доступен всегда.

### Минусы
- **Offline-first не полон.** Три класса действий защищены, остальные — нет.
- **Один канал вместо трёх.** Всё, что нужно узнать быстро, ждёт планового прохода.
- **Версию назначает клиент**, поэтому конфликт двух устройств одного автора не обнаруживается.
- **Курсор без сброса.** Разошедшиеся курсор и локальная база чинятся только переустановкой.
- **Одна застрявшая запись останавливает соседей.** Отвергнутое прохождение блокирует отправку оценок,
  потому что исключение прерывает проход до них, а счётчика попыток и карантина нет.

## Правила

1. Всякое изменение узла на сервере сопровождается записью в соответствующий журнал `sync_changes`,
   по схеме id «документ на узел». Изменение без записи в журнал клиент не увидит никогда.
2. Клиент **никогда не пишет** поля, защищённые сервером (квалификации, сертификаты, промо полок).
   Даже локально они read-only для UI.
3. Действие, меняющее серверное состояние, идёт через очередь. Прямой вызов callable из репозитория
   допустим **только** для операций, помеченных в «Отправка на сервер» как ещё не переведённые, и
   каждая такая операция — известный долг, а не разрешённый паттерн.
4. Любая операция очереди идемпотентна: повторная доставка не удваивает эффект.
5. Курсор двигается только после успешного применения изменений.
6. Для каждой фичи канал доставки выбирается явно (журнал / listener / push) — по требованиям UX и
   стоимости.
7. Сид-скрипты пишут журнал по продовой схеме id. Сид, растящий коллекцию, — баг сида.

## Маппинг из легаси

| Legacy | Новый эквивалент |
|---|---|
| `SyncInteractor` 8-step cycle | независимые `Syncable`-джобы, порядок в `SyncModule` |
| `lockServer(event)` + `rollbackStructureData` (пустой) | отменено: серверные транзакции атомарны сами по себе |
| `dataUpdateGlobal / dataUpdateLocal` | `lastModifiedAt` per-entity |
| `isUpdateStructure` (`remoteVersion > localVersion`) | `version` per-entity; из журнала — безусловное доверие серверу |
| `ChangeVersionStructure` (isCreate flag) | журнал `sync_changes` + очереди отправки |
| `SyncWorker` OneTime при старте | `SyncWorker` + `ProfileSyncWorker`, каденция из настроек |
| `isDownload: Boolean` | read-through cache в repository |
| `dataUpdateLocal == "-1"` (удаление) | отсутствие id в ответе `refreshByIds`, `archived`, пустой `visibleOn` |
| `updateRemoteQuestion` (не срабатывал) | очереди отправки, которые действительно работают |

## Отозванные решения

**Amendment 2026-04-21 — cascading sync через `contentsVersion`. Отозван 2026-08-31.**

Amendment описывал рекурсивный обход `syncLevel(...)` с early-exit по `contentsVersion`.

Он был реализован — `CascadingSyncOrchestrator` и `SyncLevel` плюс два набора тестов, коммит
`5140ae3b` от 2026-04-25 — и через пять дней удалён в `1cb9f366` («Finalize sync list architecture»)
в пользу `CatalogSyncListOrchestrator`. **Решение о замене было принято в коде и не дошло до этого
документа**, поэтому Amendment четыре месяца стоял как действующий, а сервер всё это время
проставлял `contentsVersion` во все узлы для клиента, который его не читает.

Настоящая редакция лишь записывает то, что уже сделано. Каскад выигрывает на очень большом дереве,
меняющемся редко; здесь журнал изменений и так короткий. `contentsVersion` перестаёт писаться сервером
и удаляется из клиентских моделей миграцией.

Урок, который стоит держать при себе: механизм синхронизации меняли в коде, не тронув ADR, — и
следующие четыре месяца всякий, кто открывал документ, читал про несуществующий алгоритм.

Из Amendment сохраняется одно: имя поля курсора — **`lastModifiedAt: Long`** (Unix millis).
Семантически это `updatedAt` из первой редакции, но имя самоописательнее, а `Long` проще в Room и
Firestore, чем сериализованный `Instant`.
