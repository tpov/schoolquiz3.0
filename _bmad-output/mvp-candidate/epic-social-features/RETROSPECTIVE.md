## Findings

### Из ревью этого разбора (bmad-review по 8.1/8.2 — линзы adversarial, verification-gap; краевая линза выполнена инлайн по непокрытым краям после сбоя провайдера — сужение записано)

**1. [high, чинить сейчас] `countsFor` считает распределение без оси вопроса — проценты мульти-серии неверны.** `functions/poll-views.js:122-138` фильтрует голоса только по `revisionId` (`:128`), а запрос-источник берёт все голоса серии (`:210-220`, `where("seriesId")`). Продакшн-авторинг назначает одинаковые optionId на каждый вопрос (`opt-1..opt-8`, `PollUseCases.kt:159`), дедуп сервера — в пределах вопроса, поэтому в каждой серии с >1 вопросом из UI голос чужого вопроса попадает и в `optionCounts`, и в знаменатель `respondentCount` — вопреки требованию «каждый участник посчитан в знаменателе своего вопроса однократно» (epic-8-context.md, 8.2). Тесты зелёные, потому что фикстуры используют непересекающиеся пространства id по вопросам (`poll-views.test.js:56-72`: opt-red/… против f-apple/…) — ровно то, чего в проде не бывает. Подтверждено независимо мной и линзой verification-gap (её RED-предложение: двухвопросная серия с opt-1/opt-2, голоса на q0 и q1 — сейчас такой тест зелёным не написать). Найдены обе линзы и мой прямой прочит кода.

**2. [high, чинить сейчас] `applyPublishPollSeries` не проверяет владение серией.** `functions/index.js:2612-2682`: любой аутентифицированный пользователь может прислать `polls.PUBLISH_SERIES` с чужим `seriesId` и `expectedRevisionId == текущему` — ветка бампа (`:2649-2661`) перезапишет вопросы и впишет `authorUid: uid` атакующего (`:2658`), автор и флаг `own` в обоих вью перевернутся. Ни UX-O7, ни AD-28 такого права никому не дают. Подтверждено прямым прочит кода; проверка владения в функции отсутствует вовсе.

**3. [high, чинить сейчас] Бамп ревизии — read-then-set без транзакции.** `functions/index.js:2633-2662`: чтение серии вне транзакции, затем `set()`; два конкурентных издания с разными ключами читают одинаковый `currentRevisionId`, оба вычисляют одну следующую ревизию, вторая молча затирает первую — голоса, принятые против ревизии N с содержимым A, осмысленно осиротеют под содержимым B. Образец рядом: `applyPollVote` использует `db.runTransaction` (`:2759`). Подтверждено прямым прочит кода.

**4. [medium, чинить сейчас] Очередь с голосами старого ключа после обновления карантируется молча.** Строки outbox, записанные до `402c5882`, несут ключ без `-u<uid>`; пути миграции/переписывания с фиксом не приехало. Такой ряд чужого участника отказывает как foreign-reserved и после 5 попыток уходит в QUARANTINED (`OutboxPolicy.kt:52`, `:180` — maxAttempts 5), голос не доезжает, участнику никто не сообщает. Механика карантина и отсутствие наблюдения за outbox на этом экране подтверждены мной (`OutboxPolicy.kt:43-54,180`; grep OutboxStore по social presentation — пусто); двухустройственный прогон 18.10 обошёл это через `pm clear`/свежую установку, апгрейд-путь не проверен (вывод линзы adversarial, источники её чтения).

**5. [medium, чинить сейчас] Список серий обрезается молча — вопреки собственному правилу модуля.** `poll-views.js` (list): скан серий `limit(LIMITS.maxSeries)` без громкого отказа; соседние сканы голосов (`:170`, `:211`) на потолке дают `SOURCE_TOO_LARGE` — «обрезанная правда» отказывает громко (AD-8). 51-я серия невидима всем и молча. Подтверждено прямым прочит кода.

**6. [medium, отложить к вопросу владельца] Потолок скана голосов — жёсткий кап successful-опроса.** `questionState`: на 500-м голосе серии `SOURCE_TOO_LARGE` навсегда для всех участников — агрегирующей проекции нет, только полные сканы. Успешный опрос убивает собственную статистику (~499 респондентов). Отложить до ответа владельца об ожидаемом масштабе (вопрос в Open questions); решение — транзакционный счётчик или триггерная агрегация.

**7. [medium, чинить сейчас] UI опросов не наблюдает outbox — тихие тупики.** `voteQueued`/publish-флаги живут в памяти компонента (`DefaultPollsComponent.kt:128-129, 350-370, 430-447`; подтверждено grep-ом: OutboxStore в social presentation не используется); отказ мутации (несовпадение ревизии, чужой ключ, карантин) или смерть процесса оставляют замок «Голос отправлен…»/«Серия отправлена…» навсегда, без ошибки и без §6.2-переголосования по новой ревизии. Проекция «не отправлено» из UX-O7 §4 (entityRef) не реализована на этой поверхности.

**8. [low, чинить сейчас] Карточка серии обещает продолжение с первого неотвеченного, поведение открывает вопрос 1.** `PollsScreen.kt:127-133` рендерит «Вопрос answeredCount+1 из N», `onOpenSeriesClick` (`DefaultPollsComponent.kt:77-88`) хардкодит `questionIndex = 0`. Расхождение надписи и навигации на главном пути фичи.

**9. [low, чинить сейчас] Поправка §2 живёт в контракте в виде двух конкурирующих формул.** Буллет поправки вставлен внутрь пункта — обе формулы выглядят нормативными; KDoc теста и осевые литералы (`UxO7PollVoteIdentityContractTest`) остались старого формата; journey tool строит ключи по старой формуле (`scripts/demo-fixtures/poll-journey.js`) — replay-проверки §6.1 гоняют ключ, которого приложение больше не создаёт. Утверждение владельца — отдельный открытый вопрос (давно записанный); гигиена документа/теста/инструмента — новое.

**10. [low, принять] `percentOf` — целочисленное усечение без правила округления** (`PollsScreen.kt:366-373`): 33/33/33 на трёх респондентах. Косметика; правило округления зафиксировать при случае.

**11. [low, принять] `uid` не валидируется по чарсету при попадании в `voteId`/`sourceId`** (`applyPollVote`, `PollOutboxWriters`): нестандартный uid будущего провайдера аутентификации упадёт далеко от причины. Одна строка валидации — при случае.

**12. [low, отложить] Валидация авторинга молча фильтрует пустые варианты и ренумерует** (`PollUseCases.kt:127,157`) с одной общей ошибкой без номера вопроса. UX-долг формы авторинга, не корректность.
