## 1. Что это и чего это не делает

- История операций — **read-проекция** над существующими фактами economy: строками книги
  `audit/currency_ledger/entries` (подтверждённые движения) и неразрешёнными билетами Арены
  (pending). Она не создаёт ledger-фактов, не исполняет денежных команд и не пишет ни в одну
  таблицу (AD-30: «История не исполняет денежные команды»).
- Одна проекция обслуживает **оба входа** (AD-30): общая собственная история из drawer
  («История операций») и «Начисления» конкретного авторского урока. Вторая — узкая выборка
  той же проекции (§7), а не второй источник правды.
- Прямые чтения клиентом закрытой коллекции запрещены: доступ — только авторизованные
  вызываемые view (TZ06B-семья), uid берётся из авторизации, тело вызова прав не расширяет.

## 2. Одна проекция, два входа

- `listMyOperationHistory({cursor?, pageSize?})` — общая история текущего аккаунта.
- `listMyLessonEarnings({lessonId, cursor?, pageSize?})` — «Начисления» одного авторского
  урока: те же поля, тот же порядок, курсорscoped на пару `(uid, lessonId)` (§4), доступ —
  только автору урока (сервер проверяет размещение; кураторскому чтению здесь не место).
- Оба вызова возвращают `{viewVersion, entries, pending, nextCursor}` — одна форма на оба входа.

## 3. Разрешённые поля записи (фиксируется до адаптера)

Подтверждённая запись (`entries[]`) — ровно эти поля и ничего сверх:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | идентификатор строки книги (выводится сервером, идемпотентен); в проекции — tie-break порядка |
| `atMs` | int | момент движения, серверные часы |
| `reason` | string | повод из закрытого списка `currency-ledger.js` (`attempt_reward`, `arena_author_royalty`, …) |
| `currency` | string | валюта из закрытого списка (`nolics`, `skillPoints`, `standardChargePoints`, `plasmaChargePoints`, `gold`, `boxes`, `premiumMs`) |
| `delta` | int | знаковое движение; положительное — доход, отрицательное — расход |
| `status` | `"CONFIRMED"` | подтверждённое движение (pending живёт отдельно, §5) |
| `lessonId` | string? | привязка к уроку, когда она есть в строке (`details.lessonId`); иначе null |

- `details` целиком, `sourceId`, технические поля книги и всё, что может раскрыть токены,
  order IDs и приватные payload'ы, в проекцию **не едут** (AD-30: «не раскрывает
  tokens/order secrets/private payloads»).
- Новое поле в эту форму — правка этого контракта, не адаптера.

## 4. Порядок, ничья и курсор

- Порядок — `atMs` по убыванию (новые выше), ничья — по `id` по убыванию: пара
  `(atMs, id)` уникальна, идемпотентная запись книги гарантирует уникальность `id`.
- Продолжение — ограниченная страница (`pageSize`, по умолчанию 20, потолок 20) с курсором
  «продолжай строго после `(atMs, id)` последней строки страницы»: `startAfter(atMs, id)`.
- Курсор — тот же механизм TZ06B: серверно-зашифрованная пара с scope `history:{uid}` /
  `lesson-earnings:{uid}:{lessonId}`; чужой или испорченный курсор — `INVALID_ARGUMENT`,
  а не молчаливая вторая страница. Курсор не переживает смену владельца (§8).
- Ответ без `nextCursor` — конец; `nextCursor` с пустой страницей `entries` не выдаётся
  никогда (пустая страница с продолжением — не состояние, а ошибка).

## 5. Pending против подтверждённого

- Pending — неразрешённые билеты Арены текущего аккаунта (`arena_entry_tickets` со статусом
  `RESERVED`): удержание ещё не превратилось ни в расход, ни в возврат.
- Pending едет отдельным списком `pending[]` с полями `{ticketId, atMs, currency, heldAmount,
  status: "PENDING"}` и никогда не попадает в `entries` (UX-20: «Pending is not earned»).
- Клиентский доход считают ТОЛЬКО по `entries`; pending в суммы не входит ни со знаком, ни
  без. Ожидание неизвестно-сколько — не ноль и не минус.
- Разрешение билета исчезает из pending само собой: SETTLED превращается в строки `entries`
  (ATTEMPT_REWARD/CHARGE_CLAIM), CANCELLED — в строки возврата; отдельного «прочитанного
  pending» клиент не хранит.

## 6. Ресурсы никогда не суммируются

- Нолики, очки навыка, заряды, золото, коробки и премиум-время — разные ресурсы; проекция
  отдаёт их построчно, и клиент не сводит их ни в один «общий баланс» (AD-30: «разные ресурсы
  не складываются»).
- Фильтры Все/Начисления/Расходы (UX-20) фильтруют записи по знаку `delta` внутри каждой
  валюты; «Начислено за день» имеет смысл только per-ресурс.
- Группировка по дате — по `atMs` в часовом поясе устройства; раскрытие записи показывает
  те же разрешённые поля, ничего дополнительного при раскрытии не появляется.

## 7. «Начисления» авторского урока

- Авторские выплаты помечены в книге поводом `arena_author_royalty`; строка с момента
  истории 8.6 несёт `details.lessonId` (аддитивное поле provenance, id строки не меняет).
- `listMyLessonEarnings` отбирает строки текущего uid с этим поводом и этим `lessonId`,
  тот же порядок и курсор, что в §4; ответ содержит тот же `pending: []` (у урока его нет —
  форма едина).
- Никакой агрегатной суммы сервер не считает: «сколько всего» — клиентская арифметика по
  одной валюте (нолики), и в проекцию она не возвращается.

## 8. Границы аккаунта и отсутствие денежного эффекта

- Владелец — из авторизации; `uid` в теле вызова не читается никогда. Смена аккаунта
  (owner/epoch) отсекает поздний ответ: клиент перечитывает только под текущим uid, и
  курсор, выпущенный прежнему владельцу, у прежнего владельца и остаётся (AD-30, AD-6).
- Чужая строка книги не читается ни при каком теле: выборка всегда `where uid == auth uid`.
- Чтение создаёт ноль записей: ни ledger, ни журналов, ни отметок «прочитано». Два чтения
  подряд возвращают одинаковые страницы (детерминированный порядок, детерминированные строки).

## 9. Предельные размеры

- `pageSize` 1..20, по умолчанию 20; ответ целиком — не больше `responseBytes` TZ06B
  (100 000 байт); курсор — не больше 4 096 байт. Превышение — `SOURCE_TOO_LARGE`/
  `INVALID_ARGUMENT`, а не усечение на лету.
- Количество записей истории не ограничивается проекцией: страницы продолжаются, пока есть
  строки. «Вся история одним куском» — не состояние, которое этот контракт определяет.
