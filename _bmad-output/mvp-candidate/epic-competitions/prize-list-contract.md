## 1. Субъекты и границы

- Серверный владелец соревнований (`tournament-policy.js` → `tournament-service.js` →
  `course-tournament-controller.js`) остаётся единственным источником фактов списка, мест и
  выплат. Договор не создаёт второй экономики и не переносит денежные решения на клиента
  (AD-1/AD-9: economy — единственный владелец integer wallet и резервов).
- Договор связывает ровно пять поверхностей одной версии списка: (а) CREATE — приём и
  заморозка списка и фонда; (б) reserve — эскроу-запись при CREATE; (в) read — красная
  проекция события для клиента; (г) ranking→place mapping — присвоение мест финишировавшим по
  опубликованной сетке; (д) payout — разовая выплата строк и возврат остатка при терминальном
  переходе.
- Половина O3 строки гейта («permitted proposal/confirmation/READY projections and
  restoration») — **не** предмет этого договора: она закрыта историей 5.7
  (`meeting-restore-uxo3`, `tickets.toml`). Здесь она упомянута только для честного покрытия
  строки UX-O2/O3 (§7).
- Arena season economics (AD-13), экзаменационные награды (EXAM C1, AD-9/AD-10), механика
  `currency_ledger` и premium catch-up — потребители, не цели: договор не редактирует их
  правила и не назначает им изменений.
- Никаких изменений производственного кода, конфигов, callable и поведения тестов этим
  договором не назначено: `tournament-policy.test.js` / `tournament-service.test.js` остаются
  зелёными нетронутыми. Правки исполняет история 5.4 только после утверждения (§9,
  Приложение A).

## 2. Текущая реальность призов, с которой сверяется договор

Факты baseline (все ссылки — файлы на `e7129ba6ba9197c9246825b210b195b79f0461b0`):

1. **Фиксированный DTO — единственная форма CREATE.** `validatePrizeSchedule`
   (`tournament-policy.js:84-98`) принимает объект ровно с ключами `first/second/third`
   (`:86-88`, отказ: «prizes support first, second and two thirds; no fourth place»),
   нормализует три целых суммы (`:89-92`) и считает обязательство
   `maximumLiabilityBoxes = first + second + 2*third` (`:93-94`) — третье место зарезервировано
   дважды структурой DTO. Достаточность: `fundedBoxes < maximumLiabilityBoxes` → отказ
   «insufficient prize fund» (`:95-96`).
2. **CREATE замораживает фонд и форму.** `normalizeTournamentRequest`
   (`tournament-service.js:49`, `:59-60`) прогоняет `prizes` через `validatePrizeSchedule`;
   `createEventPlan` (`tournament-policy.js:100-109`, вызов `:102`) вмораживает
   `{prizes, fundedBoxes, maximumLiabilityBoxes}` в документ события (`:188-192`); эскроу
   инициализируется `{reservedBoxes: funded, remainingBoxes: funded, paidBoxes: 0,
   returnedBoxes: 0}` (`:192`), организатору пишется эффект `RESERVE` на `-fundedBoxes`
   (`:195`).
3. **Эскроу-реконсиляция на каждой операции.** `assertEscrow` (`tournament-service.js:95-101`):
   `reservedBoxes === fundedBoxes` и `remainingBoxes + paidBoxes + returnedBoxes ===
   fundedBoxes`, иначе `INCONSISTENT_ESCROW`; вызывается на каждой мутации (`:199`, `:345`).
4. **Места — только из PLAYED-веток структуры.** `progressBracket`
   (`tournament-policy.js:324-389`, комментарий «No bronze match: real semifinal losers share
   third place» `:323`) строит placements (`:376-387`): champion — победитель финала при любом
   его статусе (`:378`), runner-up — только проигравший PLAYED-финала (`:379`), `third-upper`/
   `third-lower` — только проигравшие PLAYED-полуфиналов, слот по индексу полуфинала
   (`:380-386`). Проигравшие FORFEIT и все DOUBLE_OUT мест не получают. DOUBLE_OUT-полуфинал
   продвигает пустую сторону: финал разрешается как BYE/EMPTY (`:356-361`), и его «победитель»
   становится champion (`:378`). Статус FINISHED — при любом разрешённом финале (`:388`).
   Матрица проверена исполнением на baseline (§3, D6).
5. **Выплата — по рангу из трёх полей.** `finish` (`tournament-service.js:165-177`) вызывает
   `planPrizePayouts` (`tournament-policy.js:392-414`): сумма по рангу
   `rank===1 ? first : rank===2 ? second : third` (`:406`); placements с
   `technicalForfeit: true` пропускаются (`:404-405`; сегодня флаг всегда `false` — техническая
   фильтрация структурная, п.4); нулевые суммы не платятся (`:407`); дубликаты слота/игрока
   отвергаются (`:402-403`); `payoutId = (eventId, slot)` — фиксированные ID против повторной
   чеканки (`:391`, `:407`); `paidBoxes`, `unusedReturnBoxes = fundedBoxes − paidBoxes`,
   `returnId = (eventId, "unused-fund-return")` (`:410-413`). Эскроу финализируется одним
   писателем: `{reserved: funded, remaining: 0, paid, returned}` (`:175`).
6. **Деньги атомарны и квитированы.** Эффекты → immutable-квитанции
   `course_tournament_funding/{digest(sourceId)}` с pre-check «receipt exists before event
   settlement» и `transaction.create` (`tournament-service.js:350-359`, `:419`), записи
   `currency_ledger` (`:383-388`) и пользовательские receipts
   `users/{uid}/receipts/tournament_*` (`:389-391`); баланс организатора/получателей
   проверяется на неотрицательность (`:376-382`). Вся операция — одна транзакция с
   caught-up-циклом (`:424-435`).
7. **Красная проекция прибита к legacy.** `safeEvent`
   (`course-tournament-controller.js:86-94`) отдаёт `prizes: pick(value,
   ["first","second","third"])` (`:90`) и счётчики эскроу (`:91`); projections мест —
   `safeProgress` (`:79-85`, поля `uid/rank/slot/technicalForfeit` `:84`). Серверный
   `eventView` passthrough (`tournament-service.js:82-87`, `prizes: event.prizes` `:85`).
8. **Ничьи сняты выше призовой матрицы.** Отбор: `selectQualifiers`
   (`tournament-policy.js:167-179`) требует уникальные `uid/place` (`:174`), гейт заморозки
   требует полных непрерывных ординалов 1..16 (`tournament-service.js:124`); порядок
   tie-breakers LS сохранён решением владельца (USER-CONTINUATION-PLAN, раздел ТЗ07A).
   Матчи: `resolvePlayedMatch` (`tournament-policy.js:303-321`) сортирует
   percent → elapsed → seed (`:319`) при уникальных seed (`:308`).

## 3. Решения

Каждая строка таблицы напряжений спеки решена здесь явно; «реализует 5.4» означает «после
утверждения владельцем, в истории 5.4». Соответствие строк таблицы напряжениям: «Legacy vs new
CREATE» — D1/D2/D3/D10; «Ties in ranking» — D4; «Bracket's two semifinal losers» — D5 (+D1);
«Byes and missing rounds» — D7 (+D6); «Degenerate events» — D8; «Technical outcomes» — D6;
«CREATE retry / payout races» — D9.

- **D1. Схема v1 — упорядоченный список строк, каноническая заморозка.** Новый CREATE несёт
  `prizes = {listVersion: 1, rows: [{place, amountBoxes}, …]}`: `place` — safe integer 1..16,
  `amountBoxes` — safe integer ≥ 0, строк ≤ 16, места могут повторяться (два места 3 — норма и
  единственный способ оплатить обоих третьих). Сервер валидирует, канонизирует (стабильная
  сортировка по `(place, порядок подачи)`) и замораживает каноническую форму в документе
  события при CREATE; дальнейшие поверхности читают замороженное. Конверт запроса CREATE не
  меняется (`tournament-service.js:49` — те же `source/startsAtMs/prizes/fundedBoxes`);
  свободных текстовых меток в схеме нет (подписи мест — клиентская локализация 5.10;
  альтернатива «label в строке» отклонена: изобретает продуктовый текст без владельческого
  решения). Границы 16 — `MAX_QUALIFIERS` (`tournament-policy.js:15`): больше 16 участников и
  оплачиваемых мест не существует — `rankingGate` отвергает ranking длиннее 16
  (`tournament-service.js:124`), `selectQualifiers` режет до `MAX_QUALIFIERS`
  (`tournament-policy.js:177`); 17+ — отказ на freeze, не competitions-поверхность.
  Документный бюджет защищён. Пустой список легален
  (безпризовое соревнование: liability 0). Пустой список не требует нулевого депозита: если `fundedBoxes > liability = 0`, весь депозит возвращается организатору при финале по общему правилу излишка (D2); объект `prizes` обязателен в CREATE-конверте — опускание остаётся отказом (`obj(prizes, "prizes")`, текущая охрана сохраняется).
- **D2. Liability — сумма строк ровно один раз; излишек возвращается.**
  `maximumLiabilityBoxes` для v1 = Σ `amountBoxes` (каждая строка один раз — AD-17); сумма считается в BigInt с отказом вне safe-integer диапазона (дисциплина `int()`/`safe()` `tournament-policy.js:33-42`) — переполнение Σ шестнадцати строк невозможно пронести в эскроу; CREATE
  требует `fundedBoxes ≥ liability` (отказ «insufficient prize fund» сохраняется), баланс
  организатора проверяется как сегодня (`tournament-service.js:376-382`). Депозит может
  превышать liability; излишек возвращается организатору в `unusedReturnBoxes` при финале —
  семантика «заморожен по сумме строк» относится к обязательству, а не к запрету округлить
  депозит вверх. Отвергнуто требование строгого равенства `fundedBoxes = Σ`: его нет в AD-17,
  а оно ломало бы существующую гибкость депозита без выигрыша для консервации.
- **D3. Одна замороженная версия на CREATE/reserve/read/mapping/payout.** Список живёт в одном
  месте — `event.prizes` документа события, замороженный при CREATE вместе с `listVersion` и
  liability. Reserve (эскроу `:192`), mapping (placements → строки, §3 D5–D7), payout
  (`finish` → `planPrizePayouts`, читает `event.prizes`, `tournament-service.js:170`) и read
  (красная проекция, D10/L2) потребляют только его; ни один запрос payout/mapping не несёт
  списка. Published ranking/bracket никогда не пересчитывается под новую версию — это уже
  структурно: `bracket/outcomes/progress` хранятся на событии, `finish` исполняется один раз
  над сохранёнными placements. Молчаливой смены версии нет: после CREATE поле `prizes` не
  пишет ни один путь (проверено: `finish` пишет только `status/cancelReason/escrow/
  settledAtMs`, `:173-176`); смена версии возможна только новым событием.
- **D4. Ничьи в призы не попадают — они сняты выше.** Полных ничьих в структуре не бывает:
  отбор даёт строгий порядок (уникальные непрерывные ординалы, `tournament-service.js:124`,
  `tournament-policy.js:174`) с сохранёнными LS tie-breakers; матч даёт строгую пару
  winner/loser (percent → elapsed → seed, `:319`; проверено исполнением: равные percent и
  elapsed → побеждает меньший seed). Правило сплита одной строки между «равными» не
  существует; дублирования строки под ничью не происходит (AD-17). Одна строка платит ровно
  одному placement; мусорные входы (дубликат slot/uid, чужой ранг) отвергаются существующими
  охранами (`:402-403`, `:399-401`).
- **D5. Два третьих места — организаторские строки, назначение детерминировано; ни
  авто-дублирования, ни сплита.** Структурно чемпионат производит до ДВУХ финишистов места 3
  (`third-upper`/`third-lower`, `:380-386`). Чтобы обоим заплатить, организатор перечисляет
  **две строки** места 3 — это явное решение владельца фонда, авто-дублирование строки
  запрещено (AD-17). Назначение при k строках места p и m финишистах места p: финишисты
  упорядочены фиксированным порядком слотов (для p = 3: `third-upper`, затем `third-lower` —
  порядок добавления `:380-386`, детерминирован индексом полуфинала в сохранённой сетке);
  j-й финишист получает j-ю строку этого места в замороженном порядке строк. Финишер без
  строки не получает ничего; строка без финишера возвращается в остатке. Следствие,
  публикуемое организатору: одна строка места 3 оплачивает ровно одного третьего
  (`third-upper`), второй третий остаётся без приза — молчаливой чеканки второго третьего не
  будет. Отвергнуты: сплит одной строки пополам (изобретает деньги и дроби, нарушает «каждая
  строка — один платёж»); all-or-nothing на место (удерживает профинансированную строку без
  нужды и мстит организатору за его же список).
- **D6. Матрица технических исходов сохраняется как есть — зафиксирована, не придумана.**
  Единственный источник технических исходов — meeting-плоскость (`evaluateMeeting`/
  `technicalOutcome`, `tournament-policy.js:243-247`); игравшая сессия разрешается только
  PLAYED (`resolvePlayedMatch`, см. родственный `online-o1-timing-contract.md` §4). Матрица
  назначений (проверено исполнением `progressBracket` на baseline, `:376-388`):
  | Исход | champion | runner-up | third-upper | third-lower |
  | --- | --- | --- | --- | --- |
  | финал PLAYED, полуфиналы PLAYED | победитель финала | проигравший финала | проигравший полуфинала 0 | проигравший полуфинала 1 |
  | финал FORFEIT | победитель (явившийся) | — | по PLAYED-полуфиналам | по PLAYED-полуфиналам |

  Проигравший FORFEIT место не получает вовсе; placements с `technicalForfeit: true` сегодня не
  создаются (все пуши `:378/:379/:383-384` ставят `false`) — пропуск `:404-405` остаётся
  защитной охраной. 5.4 не вводит новых видов мест, не назначает призы технически
  выбывшим вне этой матрицы и не делает DOUBLE_OUT «победой обоих» (NO change; Приложение A,
  A4). Отвергнутая альтернатива — переработать матрицу под призовые нужды: технические
  исходы принадлежат meeting-плоскости, договор их фиксирует, но не переписывает.
- **D7. Byes и непроигранные места: платится только назначенное; остальное — возврат.** BYE/
  EMPTY-узлы мест не создают (`:356-361`); место «существует» для выплат только если матрица
  D6/D5 назначила placement соответствующей строке. 15 квалификантов → сетка 16, один bye

  списке, невоспроизводимы в этом событии и возвращаются целиком. CREATE не вправирует список

  невоспроизводимых мест уже встроена в возврат остатка.
- **D8. Дегенераты 0/1 квалификантов — полный возврат, доказуемый.** `buildBracket` возвращает

  `finish([], "CANCELLED", reason)` (`tournament-service.js:237`): payouts пусты, `paidBoxes =
  0`, `unusedReturnBoxes = fundedBoxes`, `returnId` прежний (`:410-413`); организатор получает
  единственный `UNUSED_RETURN`-эффект и полный комплект квитанций (`:350-359`, `:383-392`);
  частичных выплат нет по построению — placements пусты. Арифметика: reserved F = paid 0 +
  returned F + remaining 0; терминальный remaining = 0 (§4, таблица). Отвергнутая
  альтернатива — частичный расчёт по отвеченным попыткам квалификации: AD-17 требует полный
  возврат при CANCELLED, placements пусты по построению.
- **D9. Идемпотентность — существующие ключи, без новых механизмов.** Retry того же CREATE:
  operation receipt возвращает тот же ответ без эффектов (`tournament-service.js:148-155`;
  другое тело под тем же `operationId` — `CONFLICTING_REPLAY` `:151-153`). Новый CREATE на
  существующий `eventId` — `ALREADY_EXISTS` (`:184`): один reserve на событие навсегда.

  "prize", rowKey]` (`:407`; legacy `rowKey` = slot, v1 `rowKey` = `(listVersion, place,
  row-index)` — Приложение A, A5), возврат `["tournament", eventId, "unused-fund-return"]`
  (`:413`); каждый ключ → квитанция `course_tournament_funding/{digest}` с pre-check
  «receipt exists before event settlement» (`:356-357`) и `transaction.create` (`:358`, `:419`),
  запись ledger (`:384-388`) и пользовательский receipt (`:389-391`). Гонки: вся операция —
  одна транзакция Firestore (`:424-435`); параллельные двойные spends гасятся `create`-конфликтом
  квитанции; выплата исполняется одним терминальным переходом (FINISHED `:335` /
  CANCELLED `:237`), повторные `ADVANCE_MATCH` по терминальному событию возвращают статус
  без эффектов (`:249-252`). Повреждение «квитанция есть, эскроу не финализирован» не
  додлачивается — отказ `INCONSISTENT_ESCROW` и ручной ремонт (`:357`). Отвергнутая
  альтернатива — новые идемпотентные механизмы (отдельные payout-джобы/очередь): существующих
  ключей и одной транзакции достаточно, новые механизмы удвоили бы источники истины.
- **D10. Legacy — проекция, не миграция; выплата эквивалентна.** Старые события неизменяемы:
  хранимый `{first, second, third}` и `maximumLiabilityBoxes = first+second+2*third` остаются
  в документе, settlement исполняется по правилам создания (§6). Новые CREATE после
  принятия издания принимают только v1 — legacy DTO под новый UX не подставляется (AD-17);
  до принятия единственной формой остаётся legacy (сегодняшний код не меняется).

  неизменяемости старых событий; проекция даёт ту же выплачиваемую арифметику (L3) без записи.

## 4. Консервация фонда: инвариант и арифметика по случаям

Инвариант (NFR-1, AD-17): в любой момент `reserved = paid + returned + remaining`, где
`reserved = fundedBoxes`; терминально `remaining = 0` (`assertEscrow` на каждой операции
`tournament-service.js:95-101, :345`; финализация одним писателем `:165-177`). Каждая единица
фонда либо выплачена ровно одной строкой ровно одному uid, либо возвращена организатору;
изобретённых денег нет — сумма выплаты берётся только из замороженной строки, `paidBoxes ≤
liability ≤ fundedBoxes`.

Рабочий пример v1: `rows = [{place:1, amount:100}, {place:2, amount:50}, {place:3, amount:30},
{place:3, amount:30}]`, liability = 210, `fundedBoxes = 210`. Все случаи проверены исполнением
политики на baseline (эквивалентные legacy-прогоны и прогон матрицы D6):

| Случай | placements (D6/D7/D8) | paid | returned | Инвариант (`reserved = fundedBoxes`) |
| --- | --- | --- | --- | --- |
| 0 квалификантов | — (CANCELLED `:192-193`, `finish([], …)` `:237`) | 0 | 210 | 210 = 0 + 210 + 0 ✓ |
| 1 квалификант | — (тот же путь) | 0 | 210 | ✓ |
| 2 квалификанта, финал PLAYED | champion, runner-up; третьи невоспроизводимы (D7) | 150 | 60 | 210 = 150 + 60 + 0 ✓ |
| 2 квалификанта, финал DOUBLE_OUT | — (D6) | 0 | 210 | ✓ |
| 15 квалификантов, всё PLAYED | champion, runner-up, оба третьих | 210 | 0 | ✓ |
| 15 квалификантов, полуфинал 0 FORFEIT | champion, runner-up, `third-lower`; строка `third-upper` не назначена (D6/D5) | 180 | 30 | 210 = 180 + 30 + 0 ✓ |
| 16 квалификантов (полная сетка, без byes), всё PLAYED | champion, runner-up, оба третьих | 210 | 0 | ✓ |
| оба полуфинала DOUBLE_OUT | — (D6) | 0 | 210 | ✓ |
| организатор внёс 250 при liability 210 | любая комбинация; излишек 40 в возврате (D2) | ≤ 210 | ≥ 40 | 250 = paid + returned + 0 ✓ |

Нулевые строки (`amountBoxes = 0`) легальны: они не платятся (`:407`) и не пишут эффектов
(нулевой delta пропускается, `tournament-service.js:162-163`), консервацию не трогают.

## 6. Legacy-совместимость

- **L1. Хранимая форма неизменяема.** `{first, second, third}`, liability
  `first+second+2*third` и эскроу старых событий не мигрируют и не переписываются; их
  settlement (включая события, дожившие до adoption) исполняется по правилам создания.
- **L2. Единая проекция чтения.** Красная проекция отдаёт одну форму для обеих хранимых
  форм: `{listVersion, rows, maximumLiabilityBoxes}`, где legacy → `listVersion: 0` и строки
  `[{1, first}, {2, second}, {3, third}, {3, third}]` (проекция, не хранение: два третьих
  места DTO становятся двумя строками места 3), v1 → `listVersion: 1` и замороженные строки.
  Клиент DTO больше не видит; `safeEvent` (`course-tournament-controller.js:90`) и
  `eventView` (`tournament-service.js:85`) переключаются на проекцию. Счётчики эскроу и
  projections мест продолжают отдаваться как сегодня (`:91`, `:84`).
- **L3. Выплатная эквивалентность проекции.** Назначение legacy-проекции
  `[champion → строка (place 1, #0); runner-up → (place 2, #0); third-upper → (place 3, #0);
  third-lower → (place 3, #1)]` даёт суммы `first/second/third/third` — в точности
  сегодняшний `:406` (проверено исполнением: paid 210 при `100/50/30`, обе трети по 30),
  liability проекции = `first+second+2*third` = текущий `maximumLiabilityBoxes` (`:93-94`).
  Поэтому 5.4 вправе исполнять legacy settlement спроецированным кодом; любое расхождение
  сумм для legacy — регрессия и запрещено.
- **L4. Граница принятия.** Новые CREATE после adoption: только v1; legacy-объект отклоняется
  валидатором v1 (вместо сегодняшнего отказа «prizes support first, second and two thirds; no
  fourth place», `:87`).

Таблица совместимости (сводка L1–L4):

| Событие до adoption | `{first, second, third}` (L1, неизменно) | `listVersion: 0`, строки `[{1,first},{2,second},{3,third},{3,third}]` (L2) | проецированный код, суммы = сегодня (L3), ревалидация двухформенна (A12) | — |
