## 1. Субъекты и границы

- Режимный серверный владелец соревнований остаётся единственным источником фактов вопроса
  (выдача, deadline, expiry, терминальный исход) — AD-2/AD-31. Договор не создаёт общий режимный
  контроллер и не объединяет state machine; общими остаются identity, canonical answers,
  redaction, идемпотентность, арифметика и — единственное подтверждённое общее временное правило —
  переход после вопроса AD-31.
- Договор связывает ровно три поверхности соревнований: (а) сессии квалификации (`kind =
  "QUALIFICATION"`), (б) сессии матчей чемпионата (`kind = "MATCH"`), (в) неизменность
  координационной математики C/READY, от которой зависят (а) и (б). Когортный cutoff связан
  через (а).
- Экзамен не связывается: EXAM:AD-3/AD-15/AD-30 действуют как есть, без перезаписи (O2 §4.1/§8).
  Ordinary и Arena не связываются: офлайн-пути не становятся онлайн, их адаптеры этот документ
  не ждут и не меняют. `functions/lesson-question-window.js` — принятая механика O2 — не
  редактируется этим договором и историей 5.6 как целью правки: соревновательный адаптер
  компонуется с ней, а не переписывает её (§5, Приложение A, строка A2).
- Никаких изменений производственного кода, конфигов, callable и поведения тестов этим договором
  не назначено: политики `tournament-policy.test.js` / `tournament-session.test.js` остаются
  зелёными нетронутыми. Правки исполняет история 5.6 только после утверждения (§8).

## 2. Текущая реальность времени, с которой идёт сверка

Факты baseline (все ссылки — файлы на `280593004e154f7ef333a512af6c77bb48352eca`):

1. **Конверт сессии создаётся один раз и никогда не двигается.** Квалификация:
   `tournament-service.js:219-220` — `endsAtMs: Math.min(add(at, form.maxDurationMs),
   event.qualification.endsAtMs)` с намеренным комментарием «Qualification closes at its fixed
   cutoff, including a late-started timed-out session». Матч: `tournament-policy.js:293-294` —
   `endsAtMs = startedAtMs + c.duration`, где `startedAtMs = max(готовности)` (`:292`).
   Продлевающего писателя нет; структурная охрана — `tournament-session.js:121`:
   `session.endsAtMs - session.startedAtMs > duration` даёт `SCORING_UNAVAILABLE`, то есть
   конверт длиннее суммы времён вопросов невозможен без отказа скоринга.
2. **Клэмп вопроса.** `tournament-session.js:249` —
   `questionEndsAtMs = Math.min(add(at, form.questions[questionIndex].maxDurationMs), endsAtMs)`;
   тот же клэмп при создании — `tournament-service.js:93`. Для позднего старта квалификации
   конверт уже сжат cutoff когорты, поэтому клэмп — единственный механизм, которым конверт
   остаётся фиксированным.
3. **Своевременность и видимость.** `tournament-session.js:142` и `:210/214` — текущий вопрос
   виден и ответ принимается, пока `now < Math.min(questionEndsAtMs, endsAtMs)`.
4. **Закрытия.** `tournament-session.js:227-229` — `ANSWER` (своевременный ответ), `TIMEOUT`
   (по `questionEndsAtMs`), затем `FORCED_CUTOFF` для всех оставшихся вопросов по `endsAtMs`
   (sweep выполняется операцией/worker-проходом, AD-23).
5. **Окна нет.** Сегодняшний план (`planTournamentSessionOperation`) стартует часы следующего
   вопроса в той же операции, что закрыла предыдущий (`tournament-session.js:247-248`):
   разрыва между вопросами нет вообще, поэтому окно AD-31 в турнирных сессиях пока не живёт —
   это и есть несоответствие, которое гейт запрещает объявлять соответствием.
6. **Когортный cutoff абсолютен при создании.** Старт квалификации запрещён вне
   `[qualification.startsAtMs, qualification.endsAtMs)` (`tournament-policy.js:158-160`,
   `OUTSIDE_QUALIFICATION_WINDOW`); клэмп создания (п.1) не даёт конверту пересечь cutoff;
   заморозка ранжирования привязана к точному cutoff (`tournament-service.js:117`,
   `snapshot.endsAtMs !== event.qualification.endsAtMs` → `INVALID_RANKING`).
7. **Матчательная арифметика удерживает конверт внутри этапа.** C = `stageEndsAtMs −
   READY_WINDOW_MS − sharedForm.maxDurationMs` (`tournament-policy.js:209`, `:228-230`);
   слот ≤ C (`:237`), READY строго внутри `[slot, slot+1h)` (`:288`), старт =
   max(готовности) `< slot+1h` ⇒ `endsAtMs < stageEndsAtMs` — гарантия выводится из принятых
   правил AD-17 и охраняется form-fit инвариантом `sharedForm.maxDurationMs <
   STAGE_DURATION_MS − READY_WINDOW_MS` (`:205-207`). Отдельного клэмпа в коде нет — guarantee
   выводимый, и 5.6/5.7 не имеют права его ослаблять (Приложение A, строка A7).
8. **Механика окна O2.** `lesson-question-window.js`: константа 60 с (`:43`), детерминированный
   id окна по паре (attemptId, completedQuestionIndex) (`:68-75`), захваченная конфигурация при
   открытии (`:89-110`), вердикты выдачи `ISSUE/DELIVERED/WINDOW_EXPIRED/NO_WINDOW` (`:140-161`),
   ready-ACK без перезакрепления deadline (`:181-206`).

## 3. Решения

Каждая строка таблицы напряжений спека решена здесь явно; «реализует 5.6» означает «после
утверждения владельцем, в истории 5.6». Соответствие строкам таблицы напряжений спека:
«окно ↔ endsAtMs сессии» — D1/D4; «окно ↔ cutoff когорты» — D2; «окно ↔ конец этапа/матча» —
D1/D4 и строка матча таблицы §4; «окно ↔ клэмп вопроса» — D3/D5; «окна подряд» — D9;
«первый вопрос» — D6; «C/READY» — D7.

- **D1. Конверт побеждает всё; расширений нет — ни одного, даже явного.** `endsAtMs` сессии
  фиксирован при создании (квалификация: клэмп на cutoff когорты; матч: старт + длительность
  формы) и не двигается ни окном, ни выдачей, ни retry, ни worker'ом. Бюджет: конверт сессии.
  Основание: суммарный бюджет формы уже исчерпывает конверт (`tournament-session.js:121`
  отвергает конверт длиннее суммы времён вопросов), сдвиг любого `endsAt` сдвинул бы общий
  deadline для других участников (соперника, когорты, сетки) — ровно то, что гейт
  запрещает; поэтому оговорка Never «bounded exception allowed» здесь НЕ используется: исключений
  на продление нет ни для одной поверхности.
- **D2. Cutoff когорты абсолютен.** Попытка существует только внутри
  `[qualification.startsAtMs, qualification.endsAtMs)`; окно никогда её не продлевает: конверт
  каждой сессии уже зажат cutoff при создании (клэмп `tournament-service.js:219-220` — остаётся
  без изменений), а D1 запрещает движение `endsAt`. Попытка, не завершённая к cutoff,
  закрывается существующим sweep'ом `FORCED_CUTOFF` по `endsAtMs` (`tournament-session.js:229`)
  и попадает в когорту отвеченной частью — как сегодня; попытки «после cutoff» не существует,
  поэтому вопрос «кто входит в когорту» окно не затрагивает вовсе (потребность 5.5 закрыта:
  скоуп когорты не меняется). Целостность когорты выше окна: заморозка расчёта привязана к
  точному cutoff (`tournament-service.js:117`), любое продление сломало бы freeze.
- **D3. Окно живёт внутри конверта и обрезается только им — явно, а не молча.** После закрытия
  вопроса k (своевременный ответ или исходный expiry — O2 §2) открывается окно следующего
  вопроса с захваченной конфигурацией: `windowSeconds = min(60, endsAtMs − момент закрытия)`,
  где 60 — существующая серверная константа по умолчанию (`NEXT_QUESTION_WINDOW_SECONDS`,
  `lesson-question-window.js:43`; SPEC Constraints). Захваченное значение фиксируется в
  документе окна при открытии и не меняется (captured config, O2 §3); укорочение видно клиенту
  в самом окне — молчаливого урезания нет: правило опубликовано этим договором, значение
  наблюдаемо, применяться может только на краю конверта. Пока до края далеко, окно всегда
  полные 60 секунд. Бюджет: остаток конверта; приоритет: конверт > окно (окно режется первым),
  время ответа уже выданного вопроса окном не режется никогда (AD-31; режет только
  существующий клэмп конверта, п.2 §2). Если момент закрытия вопроса лежит на краю конверта
  (остаток ≤ 0), окно не открывается — попытка немедленно завершается по D4; отрицательного
  окна и отрицательного резерва не бывает. В документе окна при открытии фиксируются также
  `openedAtMs` и `expiresAtMs = openedAtMs + windowSeconds` (как в механике O2,
  `lesson-question-window.js:89-110`), чтобы crash-recovery sweep детерминированно
  перевычислял край; sweep пишет `closedAtMs = захваченный expiresAtMs`, никогда момент
  наблюдения.
- **D4. Выдача стартует часы; expiry окна завершает попытку.** Часы вопроса k+1 стартуют
  серверным моментом выдачи внутри окна: `questionStartedAtMs = момент выдачи`,
  `questionEndsAtMs = min(момент выдачи + maxDuration(k+1), endsAtMs)` — формула клэмпа
  сохраняется, меняется только `now` (сегодня `at` операции, станет момент выдачи; O2 §5 —
  не-exam правило). Окно истекло без выдачи → режимный владелец завершает попытку: все
  оставшиеся вопросы (включая невыданный) закрываются без ответа существующим скорингом
  (null-ответ через существующий scorer, без paid-correct), kind записи — `FORCED_CUTOFF`,
  `closedAtMs` = захваченный край окна (дивергенция от сегодняшнего «FORCED_CUTOFF только по
  endsAtMs» — Приложение A, строка A3); это тот же терминальный исход, что и край конверта:
  два пути, одно состояние. Driver края — server-owned sweep/controlled tick (AD-23), никогда
  клиентский запрос; проверка края замыкается с двух сторон — и на sweep, и на самой выдаче
  (вердикт терминации по истёкшему окну, A4), поэтому выдача после края невозможна при любом
  порядке событий. Без победы таймаутом и без платных эффектов (AD-31). Метки терминала —
  серверные факты записи; клиентская проекция исхода (что игрок видит при досрочном
  завершении) — решение историй 5.9/5.10, существующий settled-ответ остаётся формой ответа.
- **D5. Своевременность и видимость — прежние min-правила; окно не создаёт второго секундомера.**
  Ответ на выданный вопрос своевременен, пока
  `первый серверный приём < min(questionEndsAtMs, endsAtMs)` (`tournament-session.js:210/214`
  — без изменений); retry возвращает тот же вопрос с серверным остатком (O2 §7); переподключение
  часы не останавливает и не перезапускает; вторых часов нет (AD-31 non-negotiables). Пока окно
  открыто и не выдано, активного вопроса нет: операционная видимость
  (`tournament-session.js:142`) и read-проекция (`tournament-service.js:451-454`) обязаны
  требовать состоявшейся выдачи текущего вопроса (Приложение A, строка A4).
- **D6. Первый вопрос — существующий стартовый контракт, без нового ACK-числа.** Окна существуют
  только на границах 1..19 (после закрытия вопроса с индексом 0..18); перед вопросом 0 окна нет,
  после вопроса 19 (последнего из 20, `QUESTIONS_PER_FORM`/`QUESTION_COUNT`) окна нет (AD-31,
  O2 §3). Стартовые правила цитируются как есть: квалификация — `START_QUALIFICATION` создаёт
  сессию серверным моментом `at`, часы вопроса 0 seeded при создании
  (`tournament-service.js:88-94`), вне окна квалификации старт запрещён
  (`tournament-policy.js:158-160`); матч — только сервер стартует матч при готовности обоих,
  `startedAtMs = max(готовности)` (`tournament-policy.js:291-294`), слот неизменяем (AD-17).
  Reconnect возвращает те же часы (`tournament-service.js:437-455`, «never restarts them»).
  Новое число для начального ACK этим договором не выбирается (AD-31). Ready-ACK на вопрос 0
  не выдаётся: он доставлен стартовым контрактом, а не окном; ключ
  `(identity сессии, questionIndex, windowId)` применим только к вопросам, выданным через
  окно (индексы 1..19); повтор старта возвращает те же часы без новой квитанции.
- **D7. C и READY математика не меняется — явное подтверждение, не формула.** Координационная
  фаза (PROPOSE/CONFIRM/READY) окон не содержит: окна начинаются только в `STARTED`-сессии.
  C = конец этапа − 1 ч − длительность формы (`tournament-policy.js:209`, `:228-230`);
  предложение до C, слот между server now и C, подтверждение до C и не позже слота, READY в
  `[slot, slot+1h)` — все без изменений (AD-17 имеет приоритет; скорректированной формулы нет).
  Соперники получают одинаковую пару form/fingerprint и одинаковый конверт, но окна —
  per-attempt: момент выдачи каждого свой, симметрия не превращается в общие часы.
- **D8. Скоринг нетронут.** Окно не добавляет ни нового исхода ответа, ни новой арифметики:
  цифры считаются существующим `scoreForm` (`tournament-session.js:105-135`), незакрытые
  слоты — null-ответами через тот же scorer; ответ first-write-wins; окна никогда не изменяют
  зафиксированные цифры префикса (`tournament-session.js:233`).
- **D9 (строка «BACK_TO_BACK»). Накопление ограничено конструкцией.** Открыто не более одного
  окна на границу; первое же окно, истёкшее без выдачи, завершает попытку (D4) — цепочка
  «expiry → окно → expiry без выдачи → …» длиннее одного звена невозможна. Кумулятивный бюджет
  окон ограничен конвертом: ≤19 окон × ≤60 с, целиком внутри `endsAtMs − startedAtMs` (D1);
  неограниченного накопления нет. Терминальное состояние — существующее SETTLED, в котором
  оставшиеся вопросы закрыты без ответов (D4/D8).

## 4. Бюджет и приоритет: что чего ограничивает

Приоритет краёв (глобально): server/UTC authority (NFR-4) → фиксированный конверт `endsAtMs`
(D1) → исходный deadline уже выданного вопроса (AD-31; только клэмп конверта) → окно (D3,
режется первым) → момент выдачи (стартует часы, O2 §5). Ни на одной поверхности окно не
продлевает общий deadline; единственное урезание окна — край конверта, объявленный здесь явно
(D3).

| Поверхность | Чем ограничено | Бюджет времени | Кто побеждает на краю |
| --- | --- | --- | --- |
| Сессия квалификации | cutoff когорты (клэмп создания) + сумма времён вопросов | конверт = `min(start+длительность, cutoff)`; внутри ≤19 окон × ≤60 с | cutoff: окно капится остатком конверта, попытка завершается на конверте (D1–D4) |
| Сессия матча чемпионата | арифметика встречи (слот ≤ C, READY в окне) + сумма времён формы | конверт = `startedAt + длительность` < конец этапа | конверт матча: тот же кап/терминация; оседавшая на краю сессия разрешает матч как PLAYED существующей матрицей `resolvePlayedMatch` (percent → elapsed → seed); технические исходы (FORFEIT/DOUBLE_OUT) остаются исходами meeting-плоскости (неявка/несогласие/неготовность) и таймингом вопроса внутри идущей сессии никогда не создаются; `resultDue` не двигается |
| Координационный C | конец этапа − 1 ч − длительность формы | без изменений; окон в фазе встречи нет | AD-17 (D7) |
| READY-окно | `[slot, slot+1h)` | без изменений | AD-17 (D7) |
| Cutoff когорты | абсолютен | ни попытка, ни окно не пересекают его | целостность когорты > окна (D2) |

## 5. Композиция с ONLINE-O2 (принятое издание, blob `e142341e…`)

- **§2 (событие завершения):** для турнирных сессий завершение вопроса — ровно существующие
  факты плана: принятый своевременный ответ (`ANSWER`), исходный expiry (`TIMEOUT` по
  `questionEndsAtMs`) или край конверта (`FORCED_CUTOFF` по `endsAtMs`). Не reconnect, не
  клиентский запрос, не поздний worker — совпадает с `tournament-session.js:227-229` без
  изменений.
- **§3 (окно):** одно окно на границу; identity окна — пара (identity сессии `q_…`/`m_…`,
  индекс закрытого вопроса), `windowId` — по механике O2 (`mintWindowId`); повтор запроса
  следующего вопроса возвращает тот же вопрос с серверным остатком окна; выдача — серверная
  отправка разрешённого вопроса; захваченная конфигурация — 60 с по умолчанию с капом конверта
  (D3) и `maxDuration` следующего вопроса.
- **§4 (ready-ACK):** квитанция ключуется `(identity сессии, questionIndex, windowId)`;
  идемпотентна; правило не-экзаменационного режима — часы стартуют выдачей (D4), первый ACK не
  закрепляет и не перезапускает deadline (O2 §4/§4.1: экзаменационное правило не обобщается).
- **§5 (answer-clock):** старт только от выдачи; никогда от reconnect, запроса или позднего
  worker; повторный запуск часов запрещён; между краем окна и стартом часов неограниченной паузы
  нет — истёкшее окно это терминация (D4), а не подвешенное ожидание.
- **§7 (потеря ACK):** потерянный ACK не создаёт нового окна и не заменяет часы — часы уже идут
  с выдачи; retry возвращает тот же вопрос с серверным остатком; по expiry окна попытка
  завершается по контракту режима (D4) без победы таймауту и платных эффектов.

## 7. Что договор НЕ делает

- Не меняет производственный код, конфиги, callable и поведение существующих тестов (все правки —

  Arena офлайн-пути; не переименовывает турнир/чемпионат.
- Не вводит второго секундомера, нового времени ответа, окна после последнего вопроса, окна перед

- Не продлевает `endsAt` сессий, концы этапов, длительность матча и cutoff когорты — исключений

- Не меняет C, READY-окно, неизменяемость слота, серверный старт матча (AD-17, D7).
- Не назначает deadlines на клиенте и не выбирает новых чисел: 60 секунд — существующая
  серверная константа; кап окна выводится из уже фиксированных серверных фактов.
