# Прогон жизненного цикла на устройствах — исполняемый сценарий

Спутник `SPEC.md`, история 11. Написан так, чтобы его отработала модель попроще:
каждый шаг — это команда, ожидаемый результат и что делать, если результат другой.

**Три правила для исполнителя. Нарушение любого делает прогон бесполезным.**

1. **Не импровизируй.** Если шаг дал не то, что написано в «Ожидаемо» — не подбирай
   обходной путь. Иди в раздел «Диагностика», собери улики, запиши в журнал и переходи
   к следующему **независимому** сценарию.
2. **Не нажимай вслепую.** Только `ui.sh ... tap <текст>`. Нажатия по координатам
   запрещены: у пяти устройств разные экраны, и один и тот же пиксель — разные кнопки.
   Прецедент: слепое нажатие ушло в чужое приложение, потому что телефон был занят.
3. **Перед каждым сценарием — снимок.** `ui.sh <serial> shot run/NN-шаг.png`. Без снимка
   провал недоказуем.

Пути ниже — от корня репозитория. Serial устройства подставляй из таблицы ролей.

## Часть 0. Подготовка

### 0.1 Устройства авторизованы

```bash
adb devices -l
```

**Ожидаемо:** пять строк со словом `device`.
**Если `unauthorized`:** на этом телефоне разблокировать экран, в окне «Разрешить отладку
по USB» отметить «Всегда разрешать» → «Разрешить». Это делает человек, не модель. Ждать,
не продолжать.

### 0.2 Роли по устройствам

Заполни таблицу фактическими serial. Роли назначены человеком заранее и не меняются.

| Роль | Serial | Что делает в прогоне |
|---|---|---|
| author | | создаёт квест, отправляет, получает отказ |
| tester | | проверка содержания |
| admin | | проверка логики |
| developer | | переносит полки, снимает с публикации |
| playerA | | играет с арены, оценивает, жалуется |

`playerB` — при пяти устройствах роль совмещает `author`: он не участвует в проверке
своего квеста, поэтому свободен как второй игрок турнира.

### 0.3 Сборка стоит везде

На устройствах может стоять **легаси 3.0.18-rc** — тот же пакет `com.tpov.schoolquiz`,
но версия выше, поэтому новая сборка поверх не встаёт.

```bash
./gradlew :apps:android-next:assembleDebug --no-configuration-cache
adb -s <serial> uninstall com.tpov.schoolquiz
adb -s <serial> install -r apps/android-next/build/outputs/apk/debug/android-next-debug.apk
adb -s <serial> shell am start -n com.tpov.schoolquiz/.apps.android_next.MainActivity
```

**Ожидаемо:** `Success`, приложение открылось на экране Home Quests.
**Если `INSTALL_FAILED_VERSION_DOWNGRADE`:** удаление не прошло, повторить `uninstall`.
**Удаление стирает данные легаси на устройстве — оно разрешено человеком именно для этих
телефонов.**

### 0.4 Uid каждого устройства

```bash
./scripts/devices/uid.sh
```

**Ожидаемо:** строка на каждое устройство с 28-символьным uid и словом `anonymous`.
Вход в аккаунт не нужен: приложение логинится анонимно само.
**Если `(no token)`:** приложение ещё не дошло до Firebase — открыть его и подождать 15 секунд.

Выпиши uid рядом с ролями в таблице 0.2. Дальше они нужны для выдачи прав.

### 0.5 Роли выданы на сервере

Права не выдаются из приложения — это отдельная работа (SPEC, CAP-7). Пока только
служебным ключом:

```bash
node scripts/devices/prepare-run.js --key <service-account.json> \
  --roles tester=<uid>,admin=<uid>,developer=<uid>
```

Сначала без `--apply` — прочитать вывод, убедиться, что uid верные. Потом с `--apply`.

**Скрипт заодно проставляет `catalogs/{id}.questType`** — без этого поля курс уедет на
арену вместо архива, и сценарий 9 провалится по причине, не связанной с самим сценарием.

**Если ключ недоступен:** те же поля выставляются руками в консоли Firestore, документ
`profiles/{uid}`: `testerLevel: 100`, `adminLevel: 100`, `developerLevel: 300`.
**Ровно 300, не 100:** проверка разработчика — «строго больше 100», сотка не сработает и
не скажет об этом.

### 0.6 Сервер обновлён

**Это переключатель всего прогона.** Сценарии 3, 7, 10, 11 и 12 проверяют то, чего в
боевом проекте ещё нет.

```bash
firebase deploy --only firestore:rules,functions --project school-quiz-89336951
```

**Ожидаемо:** `Deploy complete!`
**Если выкатка не разрешена человеком** — сценарии 3, 7, 10, 11, 12 помечаются
`ПРОПУЩЕН: сервер не обновлён` и не запускаются. Остальные идут как есть.

### 0.7 Журнал заведён

Создать `run/journal.md`. На каждый сценарий — строка:

```
| N | название | ГОДЕН / ПРОВАЛ / ПРОПУЩЕН | снимок | что увидели |
```

## Часть 1. Круг

Порядок обязателен: каждый сценарий опирается на предыдущий. Если сценарий провалился,
все зависящие от него помечаются `ПРОПУЩЕН: зависит от N`.

### 1. Автор создаёт квест `[author]`

```bash
S=<author>
./scripts/devices/ui.sh $S shot run/01-before.png
./scripts/devices/ui.sh $S tap "My quests"
```

Дальше по экрану: создать квест в каталоге **«Квесты»** (не «Курсы» — там другой путь),
название `Прогон <дата>`, один урок, в нём **два вопроса: один лёгкий, один сложный**.

**Почему именно два:** проверка перед отправкой требует хотя бы одного лёгкого и одного
сложного. С одним вопросом кнопка отправки не разблокируется, и это будет выглядеть как
поломка, хотя это правило.

**Ожидаемо:** квест виден в «My quests», статус черновика.
**Если экран создания не открылся:** `ui.sh $S text` — записать, что на экране, в журнал.

### 2. Отправка в арену `[author]`

```bash
./scripts/devices/ui.sh $S tap "арену"
./scripts/devices/ui.sh $S shot run/02-submitted.png
```

**Ожидаемо:** статус черновика сменился на «отправлен на проверку».

Проверка на сервере — документ появился:
консоль Firestore → `quest_review_requests`, свежий документ, `processed: true`,
`status: UNDER_REVIEW`.

**Если `processed: false` и есть `lastError`:** записать текст ошибки в журнал, это провал
серверного триггера. Сценарии 3–8 → `ПРОПУЩЕН: зависит от 2`.

### 3. Единица не публикует `[tester]` `[admin]` — требует 0.6

Сначала проверяем **порог**, потом уже пропускаем квест.

На `tester`: «Review» → найти квест → проверка содержания → **оценка 1**.
На `admin`: то же → проверка логики → **оценка 1**.

**Ожидаемо:** квест **не** опубликован. В `quest_review_requests` статус остался
`UNDER_REVIEW`. В коллекции `quests` документа нет.

**Если опубликовался** — это провал самой важной заплатки. Записать и продолжать: дальше
всё равно проверяем перенос.

### 4. Проверка пройдена `[tester]` `[admin]`

Те же экраны, **оценка 3** на обоих.

**Ожидаемо:** в `quests` появился документ, `visibleOn: ["arena"]`.
**Если пусто:** раздел «Диагностика», пункт «Квест не публикуется».

### 5. Квест виден на арене `[playerA]`

```bash
S=<playerA>
./scripts/devices/ui.sh $S tap "SYNC NOW"
sleep 15
./scripts/devices/ui.sh $S shot run/05-arena.png
```

Дойти до арены каталога «Квесты».

**Ожидаемо:** квест в списке.
**Важно:** до этого прогона арена была пуста во всех каталогах — это первый квест,
прошедший публикацию по-настоящему.

### 6. Игра и оценка `[playerA]`

Пройти квест целиком. **Оценка появляется только после безошибочного прохождения** —
если ошибиться, окна оценки не будет, и это не поломка.

**Ожидаемо:** результат показан, предложена оценка, оценка принята.

### 7. Перенос арена → домашние `[developer]` — требует 0.6

```bash
S=<developer>
./scripts/devices/ui.sh $S longtap "Прогон"
./scripts/devices/ui.sh $S shot run/07-menu.png
```

**Ожидаемо в меню:** «Показать в домашних», «Показать на арене», «Показать в отборочном»,
«Показать в чемпионате мира», «Вернуть в архив», «Снять с публикации всюду».

**Если только «Share»:** права не доехали. `ui.sh $S text` и в диагностику, пункт «Нет меню полок».

```bash
./scripts/devices/ui.sh $S tap "Показать в домашних"
```

**Ожидаемо:** в `quests/{id}` стало `visibleOn: ["home"]`, появилась запись в
`admin/shelf_moves`.

### 8. Квест пропал с арены `[playerA]` — главная проверка

Это то, ради чего затевался весь круг: перенос — не добавление.

```bash
S=<playerA>
./scripts/devices/ui.sh $S tap "SYNC NOW"
sleep 15
./scripts/devices/ui.sh $S shot run/08-gone.png
```

**Ожидаемо:** на арене квеста **нет**, на домашней полке **есть**.
**Если остался на арене** — либо не доехала синхронизация (подождать и повторить один
раз), либо перенос сработал как добавление. Второе — провал.

### 9. Курс в архив `[author]` `[developer]`

Создать квест в каталоге **«Курсы»**, провести через 2 и 4.

**Ожидаемо:** `visibleOn: ["archive"]`, `archived: true`. На арене курса нет.
**Если уехал на арену:** не проставлен `catalogs/courses.questType` — вернуться к 0.5.

Затем на `developer`: перенести курс в домашние, потом **вернуть в архив**.

**Ожидаемо:** возврат сработал.
**Если пункта «Вернуть в архив» нет** — сервер не обновлён, раньше возврат был невозможен.

### 10. Снятие с публикации `[developer]` — требует 0.6

```bash
./scripts/devices/ui.sh $S longtap "Прогон"
./scripts/devices/ui.sh $S tap "Снять с публикации"
```

**Ожидаемо:** `visibleOn: []`; на других устройствах после синхронизации квест исчез
отовсюду.

### 11. Отказ доходит до автора `[tester]` `[author]` — требует 0.6

Новый квест по шагам 1–2. На `tester` — отклонить с причиной `Мало вопросов`.

**Ожидаемо на `author`** после синхронизации: квест снова редактируемый черновик, причина
отказа видна.

**Это единственный путь, по которому автор вообще узнаёт судьбу своего квеста** — до
заплатки он не узнавал ничего, ни про отказ, ни про публикацию.

### 12. Жалоба и бан `[playerA]` `[developer]` — требует 0.6

`playerA` пишет комментарий к уроку и жалуется на чужой. `developer` разбирает жалобу.

**Ожидаемо:** подтверждение даёт жалобщику плюс к репутации, отклонение — минус; при
бане у автора в `users/{uid}` появляется `bannedUntilMs`, и он больше не может писать
комментарии.

### 13. Турнир `[developer]` `[playerA]` `[author]`

Перенести квест в отборочный турнир, пройти двумя устройствами.

**Ожидаемо:** оба результата записаны.
**Известное ограничение:** таблица сама не пересчитывается — планировщика нет, пересчёт
вызывается только вручную разработчиком. Места будут стоять на месте. Это не поломка
прогона, это дыра, записанная в `brownfield.md`.

## Часть 2. Диагностика

Сюда — когда шаг дал не то. **Собери улики и иди дальше**, чинить в прогоне нельзя.

### Общее начало для любого сбоя

```bash
S=<serial>
adb -s $S logcat -d -v time > run/logcat-<сценарий>.txt
grep -iE "exception|error|denied|failed|permission" run/logcat-<сценарий>.txt | tail -30
./scripts/devices/ui.sh $S text > run/screen-<сценарий>.txt
./scripts/devices/ui.sh $S shot run/fail-<сценарий>.png
```

### Нет меню полок (сценарий 7)

Причина почти всегда одна: `developerLevel` не доехал до устройства.

1. Консоль Firestore → `profiles/{uid устройства}` → `developerLevel` **строго больше 100**?
2. Если поля нет — устройство под другим uid. Перечитать `./scripts/devices/uid.sh`:
   переустановка приложения меняет анонимный uid.
3. Профиль правильный, а меню нет → на устройстве «SYNC NOW», подождать 15 секунд, ещё раз.
4. Не помогло → **деброид**, раздел ниже: посмотреть, что реально лежит в состоянии.

### Квест не публикуется (сценарий 4)

1. `quest_review_requests/{id}`: `status`? `lastError`?
2. `admin/review/lessons/{lessonId}`: есть ли `testingScore` и `logicScore`, и какие?
3. Обе **не меньше 2**? Порог — двойка, единица не публикует (это правило, не поломка).
4. Оценки на месте, публикации нет → смотреть логи функций:
   `firebase functions:log --only publishSubmissionIfReady --project school-quiz-89336951`

### Ничего не синхронизируется

1. Интернет на устройстве есть? `adb -s $S shell ping -c 2 firestore.googleapis.com`
2. В логе `PERMISSION_DENIED` → правила отвергают запрос, записать какую коллекцию.
3. В логе App Check → отладочный токен устройства не зарегистрирован в проекте.

### Деброид: заглянуть внутрь работающего приложения

Когда экран показывает не то, а логи молчат — единственный способ увидеть настоящее
состояние. Отладчик, а не нажималка: показывает переменные, не заменяет `ui.sh`.

```bash
debroid daemon &
debroid attach com.tpov.schoolquiz
```

Из ответа взять `sessionId` и подставлять дальше **дословно**.

Проверить, что приложение думает о правах:

```bash
debroid break <sessionId> DefaultQuestListComponent.kt 148 \
  --package com.tpov.schoolquiz.android.feature.quizzes_screen.presentation.component
debroid poll <sessionId> 0 --with-stacktrace
```

Долгое нажатие на квест на устройстве → снова `poll` → на срабатывании взять `threadId`:

```bash
debroid pause-state <sessionId> <threadId>
debroid eval <sessionId> <threadId> "canManagePublicShelves"
```

Досмотрел — обязательно снять точку и отцепиться, иначе приложение останется
остановленным:

```bash
debroid remove-break <sessionId> <breakpointId>
debroid detach <sessionId>
```

Не опрашивать `poll` в цикле: дважды и хватит. Если событий нет — действие на устройстве
не произошло, а не отладчик сломался.

## Часть 3. Отчёт

В `run/journal.md` к концу должно быть:

1. Таблица всех тринадцати сценариев с вердиктом.
2. На каждый `ПРОВАЛ`: снимок, кусок лога, что именно ожидалось и что получилось.
3. Отдельным списком — **что не удалось проверить и почему** (не хватило устройства,
   сервер не обновлён, права не выданы). Пропуск, названный вслух, честнее провала,
   выданного за успех.

Чего в отчёте быть не должно: догадок о причинах. Улики собирает прогон, разбирается
с ними другой заход.
