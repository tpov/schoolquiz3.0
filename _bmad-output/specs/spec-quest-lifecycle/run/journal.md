## Инцидент: adb завис после смешения двух бинарников

При попытке ускорить прогон через Maestro обнаружилось, что Maestro (`dadb`) не видит
устройства, которые видит обычный `adb` (Homebrew, версия 36.0.0). Гипотеза: конфликт с
`ANDROID_HOME`, который не был экспортирован. Экспортировал `ANDROID_HOME=~/Library/Android/sdk`
(содержит adb версии 35.0.2) — это НЕ помогло Maestro, и в процессе перезапуска серверов
двумя разными бинарниками adb сам застрял: `adb devices` перестал отвечать вообще, даже
для обычных сценариев.

**Исправление:** убил все процессы adb (`pkill -9`), снял `ANDROID_HOME`/`ANDROID_SDK_ROOT`
из окружения, поднял сервер заново только от Homebrew-бинарника — того самого, которым
весь прогон работал раньше через `ui.sh`. Ждал восстановления через `Monitor`, не слепыми
повторами.

**Урок для следующего раза:** не трогать `ANDROID_HOME` и не запускать второй `adb` рядом
с уже работающим. Если Maestro не видит устройства — сначала проверить одной командой,
видит ли их **обычный** adb с текущим окружением; если да, искать причину в самом Maestro
(dadb может требовать другой протокол авторизации), а не трогать окружение вслепую.

## Разбор: почему Maestro не видел устройства (закрыт)

Прошлая гипотеза («конфликт `ANDROID_HOME`, два бинарника adb») была **неверной** — и
именно она привела к тому, что я завалил adb. Настоящая причина найдена измерением, а не
догадкой.

`Dadb.list()` (dadb 1.2.10, внутри Maestro) не просто читает список с adb-сервера — он
перебирает **все** серийники и на каждом открывает транспорт. Два самсунга
(`R38MB08PNJA`, `RF8W80MBR3Z`) находятся в состоянии `unauthorized`; на первом же из них
открытие транспорта бросает `IOException: device unauthorized`, и **весь список падает
целиком**. Maestro получает ноль устройств и сообщает «You have 0 devices connected».

Доказательство — прямые вызовы dadb в обход CLI (`Probe.java` / `Probe2.java`, scratchpad):

| Вызов | Результат |
|---|---|
| `Dadb.list()` | `IOException: Command failed (host:transport:R38MB08PNJA): device unauthorized` |
| `AdbServer.createDadb(...,"host:transport:17e6bcfc")` + `getprop` | OK — `T775H` |
| то же для `825a8697` | OK — `23021RAA2Y` |
| то же для `JRTSU4JRMVOZFUVG` | OK — `RMX3941` |
| то же для `56271FDCH00C5S` | OK — `Pixel 10 Pro` |
| то же для `10AE2T1986003XA` | OK — `V2247` |

Вывод: adb, ключи, окружение и сами устройства **исправны**. Достаточно убрать два
неавторизованных из поля зрения adb-сервера (отключить кабель либо подтвердить на экране
телефона «Разрешить отладку по USB») — и Maestro заработает по всем пяти.

Обхода на стороне хоста нет: adb-сервер перечисляет USB-устройства автоматически, отфильтровать
их переменной окружения или ключом нельзя, а `adb disconnect` работает только для сетевых.

**Урок (дополняет предыдущий):** причину искать измерением на самом нижнем слое, который
воспроизводит отказ. Здесь это заняло четыре команды: спросить adb-сервер по протоколу,
затем дёрнуть библиотеку Maestro напрямую. Менять окружение вслепую было и лишним, и вредным.

## Сценарий 1: что выяснилось об управлении интерфейсом

Форма создания заполнена на планшете `17e6bcfc`: каталог «Квесты», квест `Progon 0309`,
раздел `Razdel`, тема `Tema`, урок `Urok`, лёгкий вопрос `Vopros legkiy 1` (верный ответ
«Verno») и сложный `Vopros slozhnyy 1` (верный «Pravilno»). На экране структуры появилась
строка «Сохраненный квест: Progon…» — черновик сохраняется сам, без нажатия «Сохранить».

По ходу нашлись четыре препятствия, каждое из которых до этого срывало прогон:

**1. Ярлыков для тестов в приложении нет ни одного.** В дереве элементов встречаются только
рамочные `android:id/content`, `android:id/statusBarBackground` и
`com.tpov.schoolquiz:id/action_bar_root`. Ни `testTag`, ни осмысленных `content-desc`, кроме
восьми штук («Назад», «Открыть меню», «К структуре», «Добавить фото», «Превью»,
«Предыдущий вопрос», «Следующий вопрос», «Добавить вопрос»). Вывод: автоматизация возможна
только по видимому русскому тексту. Это делает автотесты хрупкими к переводу — а перевод на
украинский обязателен по закону, и на Xiaomi интерфейс уже частично украинский.

**2. Поиск по подстроке брал не тот элемент.** `ui.sh` искал подстроку и брал первое
совпадение сверху, а поле каталога со значением «Квесты» стоит в дереве **выше** подписи
«Квест». То есть `tap "Квест"` всё это время нажимал поле каталога. Исправлено: сначала
точное совпадение `text`, затем точное `content-desc`, и только потом подстрока.

**3. Экранная клавиатура закрывает нижние поля.** При её появлении форма прокручивается вверх
примерно на 139 точек. Нажатие по «Тема» и «Урок» попадало в клавиатуру, фокус оставался на
прежнем поле, и ввод дописывался туда: вместо трёх значений получилось `RazdelTemaUrok` в
одном поле. Так же выяснилось, что **одной секунды ожидания мало** — дамп успевает устареть
до момента нажатия, потому что форма ещё едет. Нужны две.

**4. Кириллица через adb не вводится вовсе.** `adb shell input text "Прогон"` не доставляет
ни одного символа, поле остаётся пустым; латиница той же командой доходит. Поэтому имена в
прогоне латинские. Для ввода кириллицы нужен Unicode-ввод — либо драйвер Maestro, который
пишет текст напрямую в элемент.

Отдельная неясность, передана агенту автора: кнопка «Сохранить» приходит с
`clickable="false"` даже когда оба вопроса заполнены, и нажатие по ней ничего видимо не
меняет. Отправка на проверку пока не найдена.

## Сценарий 1 доведён до отправки: что показала база устройства

Кнопка отправки нашлась **под вкладками с вопросами**, ниже видимой части формы, поэтому при
осмотре сверху её не было видно: «Отправить на арену». После нажатия на экране появляется
«Квест на арену поставлен в очередь».

### Поправка к самому себе

Первую копию базы я снял **без журнала** (`-wal`), и она показала пустую очередь и состояние
`SAVED`. На этом основании я уже готовился объявить дефект «приложение говорит об отправке, а
не отправляет». Проверка с журналом дала обратное. Отчёт агента автора содержит ту же ошибку
(«статус остаётся Черновик») — по той же причине.

**Правило на будущее:** база Room читается только вместе с `-wal` и `-shm`. Копия одного
`.db` показывает состояние на момент последней контрольной точки, а не текущее.

### Что на самом деле в базе

Очередь отправки содержит ровно одну заявку, и она правильная:

| Поле | Значение |
|---|---|
| operation | `quest_authoring.SUBMIT_ARENA` |
| targetShelf | **`arena`** |
| entity_ref | `quest_authoring:draft:draft-3c5czdji4xc5` |
| state | `WAITING` |
| attempt_count | **0** |
| last_error | пусто |

В теле заявки — всё дерево черновика и оба вопроса: `Vopros legkiy 1` (EASY) и
`Vopros slozhnyy 1` (HARD), с верными ответами. Состояние черновика — **`REVIEW_QUEUED`**
(localRevision 4).

Вывод: **клиентская половина работает и правило владельца соблюдает** — выпуск идёт на арену,
а не куда-то ещё.

### Где цепочка обрывается

`sync_run_trace` для этого владельца: `kind=CONTENT`, `last_success_at_ms=0` — синхронизация
не удавалась **ни разу**, ветвь отказа `REFUSED`, причина `NOT_FOUND`.

`CallableErrors.kt:112-123` относит `NOT_FOUND` к окончательному отказу: «Сервер посмотрел и
отказал. Повтор ничего не изменит». Именно этот код Firebase отдаёт на вызов обработчика,
которого на сервере нет. Обработчик `"quest_authoring.SUBMIT_ARENA"` в нашем коде есть
(`functions/index.js:747`), но выкатка заблокирована и ждёт решения владельца.

### Риск, который важнее самого прогона

Окончательный отказ уводит мутацию в карантин, а карантин по AD-28 **откатывает локальное
изменение** — для этой операции откат прописан в
`shared/feature/quest-authoring/data/.../outbox/QuestArenaQuarantineRollback.kt`.

Значит при отправке на устаревший сервер автор получает не «попробуйте позже», а **тихую
потерю заявки**: `REVIEW_QUEUED` откатится, и квест вернётся в черновики. Сейчас этого ещё не
случилось только потому, что попыток отправки было ноль. Проверить это поведение до выкатки
нельзя — оно и проявится ровно в момент первой попытки.

Это стоит рассмотреть отдельно от прогона: отсутствующий или переименованный обработчик на
сервере не должен приводить к откату авторской работы. Ошибка развёртывания — не отказ по
существу.

## Почему арену никто не нашёл (закрыто)

Четыре агента независимо доложили «раздела Арена нет». Это неверный вывод из верного
наблюдения: они смотрели вкладку «ЛОКАЛЬНАЯ», а арена относится к вкладке «ИНТЕРНЕТ» —
`DrawerSection.InternetSection.Arena`.

Но и на вкладке «ИНТЕРНЕТ» её не было бы видно:

```
data object Arena : InternetSection {
    override val requiredRoles get() = mapOf(Role.USER to Title.TEACHINGS.first)
}
```

`Title.TEACHINGS.first` = **3000** очков (`Title.kt:14`). Столько же требует «Каталог»,
«Общение» требует 10000 (`PLAYER.first`).

**Следствие для замысла владельца.** Выпуск идёт только на арену — а арену не видит ни автор,
ни любой игрок до 3000 очков. То есть опубликованный квест оказывается на полке, невидимой
почти для всех, включая его собственного автора. Новый игрок не увидит арену вообще никогда,
пока не наберёт 3000. Это надо решить до релиза: либо порог арены снимается, либо выпуск идёт
не только туда.

## Выкатка сделана по решению владельца — и вскрыла главное

Владелец разрешил выкатку в боевой проект `school-quiz-89336951` и снятие порога с арены.

### Что мешало выкатке (три препятствия подряд)

1. **Java.** Предварительная проверка правил поднимает эмулятор отдельным процессом, а тот берёт
   Java из `PATH`, где стояла 17-я. Нужна 21-я и выше. Лечится не только `JAVA_HOME`, но и
   добавлением `$JAVA_HOME/bin` в начало `PATH`.
2. **Политика повторов.** Одна функция обработки покупок настроена на повтор при сбое, а такие
   Firebase требует выкатывать явным подтверждением. Подтверждено осознанно: повторная доставка
   уведомления защищена отдельной записью в `purchase_notifications`, второй раз ничего не спишется.
3. **Остаточный эмулятор.** Порт был занят эмулятором предыдущей попытки, ещё не догасшим.
   Проходит само через полминуты.

### Итог выкатки

Правила доступа **выложены** (`released rules firestore.rules to cloud.firestore`). Функции:
**18 обновились, 30 отказано**. Причина отказов одна: **исчерпана квота процессорного времени
Cloud Run на проект в регионе `us-central1`**. Отказавшие функции продолжают обслуживать
**прежним кодом** — новые версии просто не поднялись.

Ограничение известно в самом коде: `FUNCTION_OPTIONS` держит `maxInstances: 1` с пояснением
«наименьшее, что помещается в стартовую квоту проекта; поднять, когда квота будет выдана»
(`functions/index.js:123-130`).

### Поправка к себе

Я сказал «все 49 функций живут на сервере», сверившись с `functions:list`. **Это неверно.**
Присутствие в списке не означает, что функция обслуживает вызовы: она может числиться с
неудавшейся версией.

### Предсказанная потеря работы автора — воспроизведена

После выкатки я перезапустил приложение на планшете, чтобы очередь ушла. Результат:

| До перезапуска | После |
|---|---|
| очередь: `WAITING`, попыток 0 | очередь: **`QUARANTINED`**, попыток 1, ошибка `NOT_FOUND` |
| черновик: `REVIEW_QUEUED` | черновик: **`DRAFT`** |

То есть заявка автора **пропала, а состояние откатилось в черновик** — ровно тот риск, который
записан выше по журналу до того, как случился. Автору при этом ничего не сообщается.

### Корень: приёмник очереди никогда не работал

Клиент отправляет всю очередь единственным вызовом `submitMutation`
(`FirebaseMutationTransport.kt:69`). Серверные логи показывают, что этот вызов **создавался
впервые** и создание **провалилось**:

```
Could not create or update Cloud Run service submitmutation,
Container Healthcheck failed. The user-provided container failed to start
and listen on the port ... within the allocated timeout.
revision: submitmutation-00001-mof
```

Версия `00001` — то есть рабочей версии у него не было **никогда**. Остальные функции из того же
`index.js` поднялись, значит файл загружается нормально; контейнер не стартует из-за нехватки
процессорного ресурса в регионе, той же исчерпанной квоты.

**Следствие:** ни одна отложенная операция клиента никогда не доходила до сервера. Не только
отправка на арену — вся очередь. И каждая попытка уводит запись в карантин, откатывая локальное
изменение.

### Что из этого надо решать отдельно от прогона

1. **Квота.** Нужна заявка на увеличение процессорной квоты Cloud Run в `us-central1` — это
   действие в консоли облака, доступное только владельцу проекта.
2. **Откат по ошибке доставки.** Карантин при `NOT_FOUND` стирает работу автора. Ошибка
   развёртывания и отказ по существу — разные вещи, и первое не должно уничтожать локальные
   изменения. Сейчас клиент их не различает (`CallableErrors.kt:112-123`).
3. **Молчание.** Автор не получает ни уведомления, ни пометки, что заявка не ушла. Квест просто
   снова становится черновиком.

## Приёмник очереди выложен — и вскрылся тупик для автора

Точечная выкатка `firebase deploy --only "functions:review:submitMutation"` прошла:
`Successful update operation`, `Deploy complete!`. Приёмник наконец имеет рабочую версию.

После этого я попробовал отправить квест заново с планшета — и отправка **не состоялась**.
Разбор довёл до конца.

### Что произошло по шагам

1. Нажатие «Отправить на арену» даёт ошибку `IllegalArgumentException` внутри сценария.
2. Компонент переводит **любой** `IllegalArgumentException` в одно сообщение —
   `qa_error_arena_missing_questions`: «Для отправки нужны сохраненные легкие и сложные вопросы
   в каждом уроке» (`DefaultQuestCreateComponent.kt:1583`).
3. Настоящая причина другая. В `SubmitQuestDraftToArenaUseCase.kt:43`:
   `require(bundle.draft.status in SUBMITTABLE_STATUSES)`, где
   `SUBMITTABLE_STATUSES = {SAVED, SYNC_PENDING, SYNCED}` (строки 102-107). **`DRAFT` в набор не
   входит.**
4. А откат из карантина ставит именно `DRAFT` — намеренно и с пояснением
   (`QuestArenaQuarantineRollback.kt:10-14`): «карантин терминален… оставленный статус запер бы
   черновик навсегда. Откат возвращает его в `DRAFT` вместе с причиной, **тем же путём, каким
   кладётся отказ рецензента**».

### Тупик

Две половины противоречат друг другу. Откат разблокирует черновик «чтобы автор поправил и
переотправил», а путь отправки состояние `DRAFT` не принимает.

И вернуть черновик в отправляемое состояние нечем: во всей фиче ровно пять присвоений статуса
(2×`SYNCED`, 2×`SAVED`, 1×`SYNC_PENDING`), и **единственное присвоение `SAVED` стоит в
`CreateQuestDraftUseCase.kt:40`** — то есть только при создании черновика. Ни сохранение, ни
правка вопросов статус не поднимают.

**Следствие, и оно шире карантина:** тем же путём кладётся **отказ проверяющего**. Значит любой
отклонённый квест тоже становится неотправляемым навсегда. Автору остаётся только завести квест
заново с нуля.

Проверено на живом устройстве: черновик `draft-3c5czdji4xc5` содержит оба вопроса
(EASY `Vopros legkiy 1`, HARD `Vopros slozhnyy 1`), урок, тему и раздел — всё на месте, — но
находится в состоянии `DRAFT`, и кнопка отправки приходит с `clickable="false"`.

### Второй дефект: сообщение уводит в сторону

Автору говорят «нужны сохранённые лёгкие и сложные вопросы», хотя вопросы есть и дело в
состоянии черновика. Автор пойдёт чинить исправное. Причина — сваливание всех
`IllegalArgumentException` в одно сообщение, при том что сценарий бросает как минимум четыре
разных: неверный статус, неверная полка, пустой список уроков, урок не готов.

### Что чинить

1. Отказ и карантин должны возвращать черновик в состояние, из которого его **можно** отправить
   заново (или `DRAFT` должен войти в `SUBMITTABLE_STATUSES` — это решение по замыслу, не по коду).
2. Сообщения об отказе должны различаться по причине.
3. Причина отказа кладётся в `rejectionReason`, но на экране автору не показывается — у нашего
   черновика поле пустое даже после карантина.

### Мелочь, всплывшая попутно

Кнопка создания квеста на экране «Мои квесты» **имеет** описание «Создать квест» — вопреки моей
прежней записи, что она безымянная. Безымянной она была на другом экране. Поиск по описанию
работает, обходной путь по границам не нужен.

## Тупик закрыт

### Что было сломано

`DRAFT` не входил в набор состояний, из которых разрешена отправка
(`SAVED`, `SYNC_PENDING`, `SYNCED`), а отказ рецензента и карантин заявки возвращают черновик
именно в `DRAFT`. Поднять состояние обратно было нечем: `SAVED` присваивается **только** при
создании черновика.

Проверено отдельно: боевой `QuestAuthoringRepositoryImpl.upsertQuestion` пишет только сам
вопрос и статус не трогает — то есть даже правка вопросов черновик не «оживляла».

### Правка

| Файл | Что сделано |
|---|---|
| `domain/model/QuestArenaSubmissionRejection.kt` (новый) | шесть именованных причин отказа + `SUBMITTABLE_DRAFT_STATUSES`, куда добавлен `DRAFT` |
| `domain/use_case/SubmitQuestDraftToArenaUseCase.kt` | вместо четырёх безымянных `require` — явные отказы с типом |
| `presentation/component/DefaultQuestCreateComponent.kt` | подпись выбирается по типу отказа, а не одна на всё |
| `res/values{,-ru,-uk}/strings.xml` | четыре новых подписи в трёх языках |
| `commonTest/.../fake/FakeQuestAuthoringRepository.kt` | фейк приведён к боевому поведению |

`CONFLICT` в набор отправляемых **не** добавлен намеренно: у расхождения свой путь разрешения
(`onResubmitOverServerVersionClick`), и отправка поверх него обошла бы сверку версий.

Допуск `DRAFT` не пропускает недоделанную работу: готовность проверяется отдельно, по урокам и
вопросам.

### Почему это не поймали тесты

Фейк репозитория при сохранении вопроса поднимал статус до `SAVED`, чего боевая реализация не
делает. То есть заготовка была **добрее реальности**: в тестах черновик после правки всегда
оказывался отправляемым, и тупик был невоспроизводим. Фейк исправлен — теперь он повторяет
боевое поведение.

Это ровно тот случай, против которого написано правило про фейки в `.claude/rules/testing.md`:
расхождение фейка с боевой реализацией прячет дефект, а не находит его.

### Новые тесты (все зелёные, 42 из 42 в модуле)

- отклонённый черновик (`DRAFT`) отправляется заново — **тест, падавший бы до правки**;
- уже поданный (`REVIEW_QUEUED`) отклоняется с причиной `DraftNotSubmittable`, и в отказе назван статус;
- урок без обеих сложностей — `LessonNotReady` с именем урока;
- чужая полка — `UnsupportedTargetShelf` с её именем;
- пустой список уроков — `NoLessonsChosen`.

### Поправка к записи выше

Ранее я записал, что «причина отказа кладётся в `rejectionReason`, но у нашего черновика поле
пустое». **Это неверно** — я смотрел устаревшую копию базы. В базе устройства
`rejectionReason = NOT_FOUND` (9 символов), то есть причина сохраняется исправно.

Настоящий пробел в другом месте: `rejectionReason` доходит до domain-модели `QuestDraft`, но в
`android/` не упоминается **ни разу** — то есть до экрана не доезжает. Автору по-прежнему не
показывают, почему заявка не прошла. Данные есть, показа нет.

Отдельно: хранимая причина технична (`NOT_FOUND`). Для отказа рецензента там будет человеческий
текст, а для сбоя доставки — код ошибки, который автору ничего не говорит. Показ причины стоит
делать вместе с переводом технических кодов в человеческие формулировки.

## Проверка правки на живом устройстве

Сборка с исправлением поставлена на планшет поверх прежней, данные сохранены.

**Тупик закрыт и в бою:** черновик в состоянии `DRAFT` (тот самый, куда его вернул карантин)
приняли к отправке — «Квест на арену поставлен в очередь». До правки на этом месте выдавалось
«Для отправки нужны сохраненные легкие и сложные вопросы в каждом уроке», и отправить его было
нельзя вовсе.

**Сообщения теперь честные.** Когда отправка ушла на пустой черновик, отказ «урок не готов»
оказался верным по существу — и это видно, потому что подписи разведены по причинам.

### Найден ещё один дефект: нельзя открыть выбранный черновик

`DefaultMyQuestsComponent.onDraftClick` (строка 140-142) **игнорирует свой аргумент**:

```kotlin
override fun onDraftClick(draft: DraftQuestDisplayItem) {
    navigator.goTo(Destination.OpenQuestCreate)
}
```

Редактор открывается на «активном» черновике, а не на том, по которому нажали. При двух
черновиках нажатие на первый открывает второй. Именно поэтому форма казалась пустой, и именно
поэтому первая попытка переотправки уходила не на тот квест.

В базе это видно прямо: у черновика с двумя вопросами `isActive = 0`, у пустого дубля
`isActive = 1`.

### Цепочка до сервера всё ещё не замыкается — но причина сменилась

Ошибка перестала быть «не найдено» и стала **`UNAUTHENTICATED`**. То есть приёмник
`submitMutation` теперь отвечает — выкатка помогла. Отвергается уже сам вызов.

Проверено:

| Что проверил | Результат |
|---|---|
| вход на устройстве | есть, `LgoyWuOIUGTbXXyXY57KeUAFvpo2`, анонимный |
| гонка при старте | **не она** — ручная «Синхронизировать сейчас» на прогретом приложении даёт тот же отказ |
| устаревший аккаунт | **не он** — vivo с созданной сегодня новой записью получает ровно тот же отказ |
| проект приложения | совпадает с проектом выкатки (`school-quiz-89336951`, пакет `com.tpov.schoolquiz`) |
| журнал устройства | `FirebaseFunctionsException: UNAUTHENTICATED` на каждой попытке |
| серверная проверка | `requireAuthUid` бросает `unauthenticated`, когда `request.auth` пуст; отсутствие профиля дало бы `not-found` — значит до сервера не доезжает сам токен |

`last_success_at_ms = 0` **на всех устройствах** — то есть путь через вызовы не срабатывал ни
разу ни у кого. Прямые чтения при этом работают: на vivo лежит 31 квест, приехавший мимо этого
пути.

**Наиболее вероятная причина, которую нельзя проверить без консоли облака:** функции второго
поколения — это службы Cloud Run, и вызов без учётной записи разрешён им отдельной выдачей прав
(`allUsers` как invoker). Выкатка обычно ставит её сама, но сегодня она прошла **частично** — из
49 функций 30 не поднялись по квоте, а `submitMutation` вообще создавался впервые. Если выдача
прав не применилась, Cloud Run отвечает отказом на неаутентифицированный вызов, и SDK показывает
его как `UNAUTHENTICATED`. Второй кандидат — включённая проверка App Check.

**Что нужно от владельца в консоли:** убедиться, что вызываемые функции разрешают вызов
(invoker `allUsers`), и проверить настройки App Check. Плюс заявка на процессорную квоту, без
которой оставшиеся 30 функций так и не поднимутся.

### Ещё одно подтверждение опасности отката

Каждая из трёх попыток отправки завершилась карантином и откатом черновика в `DRAFT`. Теперь
благодаря правке автор может отправить заново — но сама заявка каждый раз уничтожается молча.
История 14 («не уничтожать работу автора при сбое доставки») от этого только важнее: ошибка
доставки повторилась трижды подряд и трижды стёрла заявку.

## Причина возврата доведена до автора

Теперь строка в «Моих квестах» показывает, почему работа вернулась. Технические коды доставки
(`NOT_FOUND`, `UNAUTHENTICATED` и прочие) сводятся к одной честной фразе «не удалось отправить на
сервер, попробуйте ещё раз» — код автору ничего не говорит и выглядит как поломка приложения.
Человеческий текст рецензента показывается как есть.

Правка прошла через все слои: запрос сводки в DAO, проекция, модель сводки, мэппер, элемент

## Открытие выбранного черновика

Обработчик нажатия принимал элемент списка и **не использовал его**: уводил на экран создания,
а тот открывал черновик, который числился активным. С двумя черновиками автор попадал не туда,
куда нажал, и признака подмены не было никакого.

Выбран путь «сделать выбранный активным», а не «протащить идентификатор через навигацию».
Причина: редактор и так открывает активный черновик, «активен ровно один» — уже существующее
правило (при создании черновика прочие снимаются), и в базе для этого уже был запрос
`deactivateOtherDrafts`. Менять точку назначения значило бы трогать общую оболочку и её тесты
ради того, что уже выражено в модели.

| Слой | Что добавлено |
|---|---|
| база | `markDraftActive` + `activateDraft` одной транзакцией: между снятием и установкой не должно быть состояния «активны двое» или «ни одного» |
| источник данных | `activateDraft(ownerUid, draftId)` |
| репозиторий | то же, с `Result` |
| domain | сценарий `OpenQuestDraftUseCase` |
| экран | нажатие сначала записывает выбор, затем переходит — иначе экран успел бы прочитать прежний активный |

Тест: два черновика, активен второй; открытие первого делает активным его и снимает признак со
второго. До правки он падал бы, потому что выбор вообще не доходил до данных.

## Осталась вторая, отдельная беда со входом

Вытягивание содержимого (`kind=CONTENT`) не удавалось **ни разу ни на одном устройстве** —
`last_success_at_ms = 0` и на планшете, и на Realme, и на vivo со свежей установкой. Причина
`UNAUTHENTICATED`, и приходит она от самого кода функции (`requireAuthUid`), то есть токен до
сервера не доезжает.

Проверено и отброшено:
- анонимный вход в проекте **включён** (консоль Firebase, «Sign-in method»);
- у каждого устройства **есть** свой uid (`uid.sh` читает их из кеша);
- клиент функций берётся по умолчанию (`FirebaseFunctions.getInstance()`), то есть должен
  прикладывать токен сам.

Значит копать надо дальше: либо вход не успевает завершиться к моменту вызова, либо токен не
обновляется. Это отдельная работа, и она блокирует всю серверную половину прогона так же, как
блокировал закрытый приёмник.

Довести проверку до конца сейчас нельзя: устройства отключены от кабеля, остался один Realme.

## Настоящая причина «беды со входом»: недостижимые функции

Ошибка `UNAUTHENTICATED` на всех устройствах оказалась **не про вход**. Проверено и отброшено:
анонимный вход в проекте включён, uid у каждого устройства есть, клиент функций берётся по
умолчанию, App Check у функций **не применяется** (консоль, вкладка «APIs» — у Storage, Realtime
Database и Firestore стоит «Unenforced», у Functions вообще нет переключателя).

Причина в другом. Право на вызов службы Cloud Run выдаётся при её **создании**. У функций,
созданных недавно, оно по умолчанию не выдаётся, а последующие выкатки идут как «обновление» и
его не добавляют. Такая функция числится в списке, отвечает `403` HTML-страницей раньше, чем
запрос доходит до кода, — а клиентский SDK переводит это в `UNAUTHENTICATED`. Отсюда и обманчивая
картина «токен не доезжает».

Первый прогон подряд дал «закрыты 30» и был **неверен**: Google отвечает `429` при частых

Из двенадцати закрытых **четыре закрыты правильно**: `aggregateQuestRatingsDaily`,
`reconcileCurrencyBalancesDaily`, `reconcileQuestReviewDaily` (расписания) и

**Восемь сломаны:** `getEconomyConstants`, `unlockLesson`, `verifyPurchase`, `wearLogo`,

### Правка в коде, чтобы не повторилось

Заведён отдельный набор настроек для всего, что зовёт клиент, с явно объявленным входом.
Расписаниям и триггерам он **не передаётся** — их вызывает Google под служебной личностью, и

## Стена оказалась в квоте процессора — и она измерена

Выкатка восьми недостижимых функций оборвалась на первой же: «Quota exceeded for total allowable
CPU per project per region». Обходной путь через консоль тоже не прошёл — служба висит в
состоянии неудавшегося обновления, а любое изменение требует новой версии, на которую квоты нет.

Числа со страницы квот проекта:

| Квота | Предел | Занято |
|---|---|---|
| Total CPU allocation, milli vCPU, `us-central1` | **20 000** (20 ядер) | **95,5 %** |
| Total memory allocation, `us-central1` | 42,95 ГБ | 12,19 % |

Каждая функция просила **целое ядро**, функций 49 — при пределе в 20. Отсюда всё: и провал
первого создания `submitMutation`, и «healthcheck failed» у трети функций при большой выкатке, и
то, что восемь вызываемых так и остались недостижимыми. Память при этом свободна на 88 % — узкое
место одно, процессор.

### Что сделано

`cpu: "gcf_gen1"` в общих настройках функций: это штатный способ вернуть тот объём процессора,
который выделялся функциям первого поколения — для 256 МБ примерно шестая часть ядра. Суммарный
аппетит падает с ~49 ядер до ~8, и все функции помещаются в нынешнюю квоту без обращения в
поддержку.

**Цена названа честно:** при доле ядра инстанс обслуживает один запрос за раз — одновременность
больше единицы при `cpu < 1` запрещена (`options.d.ts:93`). При нынешней нагрузке (221 вызов за
неделю по данным консоли) это незаметно. Когда нагрузка вырастет, правильный ход — просить
увеличение квоты и возвращать целое ядро, а не молча упираться в очередь.

Серверные тесты после правки — все зелёные.
