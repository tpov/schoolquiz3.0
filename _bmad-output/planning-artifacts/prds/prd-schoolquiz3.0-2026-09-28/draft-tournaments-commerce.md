## Создание и обнаружение турнира по допущенному материалу

**Возможность.** Организатор создаёт отдельное событие из проверенного архивного курса либо допустимого источника уроков Арены; участник может найти событие и понять источник, сроки, состояние и призы.

**Проверяемое принятие:**

- Создание начинается со страницы архивного курса или допустимого источника Арены. Источник и автоматическая подготовка вопросов показаны до подтверждения.
- В банк входят проверенные вопросы; опросы без правильного ответа исключаются. Сервер заранее закрепляет три EASY-формы и HARD-формы, каждая требуемого размера 20 вопросов. Новые тексты во время матча не генерируются.
- Недостаток подходящих вопросов блокирует создание до резерва фонда. Неуспешное создание не выглядит в UI успешным событием.
- Архивный курс остаётся в библиотеке; событие не переносит весь курс на другую полку. Placement/rating/price/history каждого урока сохраняют самостоятельность.
- Повтор CREATE после потери ответа или перезапуска восстанавливает то же событие без второго фонда.
- Поиск/список событий и собственных сессий имеет ограниченную, продолжаемую выдачу. Отсутствие разрешения, ненайденное событие, незавершённый запрос и неизвестный исход различимы; ожидание не превращается в бесконечный опрос.
- Организатор видит first, second и third **для каждого** из двух третьих мест; до confirm показана полная сумма `first + second + 2 × third`, после — авторитетное подтверждение резерва.

Источники: C:7–10,33–35,40; T07:34–35,38; T08:3,20–32.

## Три отбора и опубликованный посев

**Возможность.** Участник проходит три отдельные EASY-попытки в течение недели, а система публикует детерминированный top16 по согласованному относительному рейтингу.

**Проверяемое принятие:**

- Показаны три distinct rounds: доступен, завершён, ожидает подтверждения или срок истёк. Для каждого round — одна зачётная попытка. Потеря ответа не запускает следующий round автоматически.
- Исходы приняты в пределах server deadline; после замораживания к cohort не дописываются поздние результаты.
- Посев берётся только из опубликованного server ranking, не из локального процента/времени и не из промежуточных строк.
- Используется весь допущенный проверенный frozen cohort. Непроверенная, отсутствующая либо повреждённая строка не пропускается; первые/последние страницы, sample или 501 строка не заменяют полный состав.
- Численная погрешность исправляется только для будущих неопубликованных расчётов с сохранением LS-модели и порядка tie-breakers. Уже опубликованные ranking/bracket неизменны.
- Calculation/rounding version, input fingerprint и результат позволяют воспроизвести происхождение ranking. Повтор/прерывание не учитывает вклад игрока дважды и не публикует частичный bracket.
- Размеры 4096/4097 служат проверкой алгоритма, а не продуктовой квотой. Превышение одного invocation budget имеет реальное продолжение к завершению; вечный Pending или автоматическая отмена не считаются принятым решением большого отбора.
- Проверки охватывают 0/1/2/15/16/17 участников, 501/502 attempts, отдельно 502 разных игрока, 1503 attempts, 4096/4097 test sizes; same-form ties, missing rounds согласно действующему контракту, malformed input, interruption/lease/retry. Фиксируются время, память и counts чтений/записей без придуманного SLA.

Источники: C:34; T07:15–22,28,42–44; T08:31–32; P:63,70–71,82.

## Договорённость, матч и возвращение после потери сети

**Возможность.** Два соперника согласуют время, проходят одну серверную сессию с одинаковой HARD-формой и видят объяснимый авторитетный результат.

**Проверяемое принятие:**

- После top16 идут этапы выбывания по три дня. Оба соперника получают одинаковый HARD-набор из 20 вопросов и совпадающий fingerprint.
- UI отдельно показывает stage deadline и крайний срок согласования; значения отображаются в локальном часовом поясе, включая DST, без изменения UTC/server deadline.
- Два игрока должны подтвердить один slot. Предложение само по себе не означает договорённости.
- Не предложивший время выбывает. Если общего времени к сроку нет — выбывают оба. Срок согласования оставляет час ожидания и длительность матча; случай отсутствия договорённости не заменяется random winner.
- Неявившегося ждут час **от согласованного времени**. Countdown показывает состояние, но не решает исход.
- После старта server clock продолжает идти при потере сети. READY/reconnect возвращают ту же session/question; Arena offline pause/checkpoint не переносится на авторитетное время турнира.
- Ответы отправляются последовательно и идемпотентно. При неизвестном исходе участник восстанавливает текущее server state, не переходит локально к следующему вопросу и не получает второй зачёт.
- Игроку доступен только разрешённый текущий вопрос; будущие формы/ключи отсутствуют в публичном состоянии, локальном хранилище и диагностике. Клиент не выбирает результат, elapsed или server time.
- Сыгранный матч решается последовательно: лучший результат → меньшее серверное время → более высокий посев. Timeout, forfeit, double-out и bye представлены согласно server event progress.
- Проверки включают один отсутствует/оба отсутствуют, нет общего времени, границу одного часа, played tie, late answer, настоящий disconnect/reconnect на устройствах, Back/rotation, RU/UK/EN и доступность.

Источники: C:35–39; T07:28–36,42; T08:24,34–48.

## Завершение турнира и сохранность призового фонда

**Возможность.** Событие доводится до итогового состояния независимо от перерывов server worker, а фонд полностью и однократно распределяется либо возвращается.

**Проверяемое принятие:**

- Фонд состоит только из коробок организатора и целиком резервируется заранее. Конкурентная другая трата не позволяет уйти в отрицательный баланс.
- Пустые позиции дают пропуски, не вымышленных участников/призёров. Менее двух допущенных приводит к отмене и одному возврату.
- Нет матча за бронзу: присуждаются два третьих места. Технически выбывшие не получают призов.
- На каждом подтверждённом состоянии `reserved = paid + returned + remaining`; после завершения remaining=0.
- Повтор reconcile/payout, crash между этапами и потеря ответа не дают второго prize/refund. Все финансовые эффекты связаны с постоянным ID и журналом.
- UI раздельно показывает pending/paid/returned; локальная анимация не начисляет коробки.
- Server-only progress закрывает qualification и продвигает матчи/технические исходы/выплаты. После crash или lease expiry процесс продолжает те же события, не теряет cursor и не блокируется навсегда на первом событии.
- Совместная проверка подтверждает final event, bracket, receipts, ledger и escrow. UI-путь идёт через реальные endpoints: course→event→3 qualifiers→seeds→propose/confirm→READY→match→result/ledger. Полный backend outcome/fund набор проверяется отдельно от одного демонстрационного матча.

Источники: C:38–41,49; T07:24–44; T08:29–30,40–48.

## Витрина золота и согласованное представление premium

**Возможность.** Пользователь видит корректные доступные предложения и сравнивает полный платёж и выгоду premium без ошибочного обещания подписки или другой цены.

**Проверяемое принятие:**

- Витрина содержит золото 10/60/150 и premium 1/7/30/365 дней за золото и через Play. Полезные существующие товары/навигация сохраняются; противоречащие новому договору позиции заменяются.
- Принятые цены за золото: 1 день — 1; 7 дней — 5; 30 дней — 15; 365 дней — 100. Ранее обсуждавшиеся 3 дня за 1, 30 дней за 10, год за 150/200 не используются.
- Отдельный экран premium имеет золотое оформление. Полная цена выбранного срока видна явно; именно она списывается.
- Рядом показана стоимость «в пересчёте на 30 дней»: 30; ≈21,4; 15; ≈8,2 золота соответственно. Это сравнение `цена × 30 / дни`, не помесячный платёж и не предложение купить дробную часть срока.
- Экономия сравнивается с покупкой такого же количества дней по 1 золоту/день: неделя ≈29%, 30 дней 50%, год ≈73%. База названа явно; расчёт использует исходные цены/длительность до округления показателей.
- Server constants задают gold prices и действующие предложения; UI не выбирает произвольную цену. Каждая покупка серверно проверяется.
- Денежная цена, локализованная валюта и доступность Play берутся из актуального store offer. Отсутствие SKU/цены означает unavailable с причиной; интерфейс не выдумывает деньги, SKU и успешную покупку.
- RU/UK/EN показывают ясные сроки/способы оплаты и защищают от repeated tap. Play-предложения не меняются автоматически вслед за новым gold pricing.

Источники: C:47; T09:13–18; D: «Подтверждённые цены premium за золото», «Подтверждённое представление premium», «Процент экономии»; M: финальные decisions gold catalogue/comparison/savings.

## Действие premium и точная граница срока

**Возможность.** Premium действует ровно в предоставленные интервалы и корректно сочетается с другими начислениями, восстановлением зарядов и возвратами.

**Проверяемое принятие:**

- Premium даёт цвет ника, отдельную ежедневную коробку без рекламы и восстановление обычных и plasma зарядов ×2.
- UI различает active, expired, unknown freshness, pending purchase и pending refund; постоянный boolean не заменяет действующие grants.
- На границе expiry преимущества прекращаются корректно.
- Обе регенерации учитывают реальные premium-интервалы и сохранённые остатки времени, включая пересечение нескольких grants и holds. Countdown представляет, а не авторитетно начисляет ресурс.
- Gold purchase, gift и Play grant сохраняют самостоятельное происхождение. Отзыв одного не обнуляет остальные.
- При возврате снимается только ещё не использованный остаток конкретного grant; использованное время, прочие покупки/подарки и правильные интервалы обеих regen сохраняются.
- Проверки охватывают expiry boundary, overlapping grants, spent/part-used/unspent, обе regen ×2, holds и account switch.

Источники: C:46,48–49; T09:16–17,38–42; T10:16,23,29.

## Ежедневные коробки и устойчивое открытие

**Возможность.** Игрок получает положенные daily коробки и открывает общий запас, сохраняя один результат при повторах и потерях связи.

**Проверяемое принятие:**

- Один тип коробки и общий баланс; разрешённые источники не ограничиваются daily.
- Ежедневная серия даёт максимум одну обычную коробку в день, premium — отдельную ежедневную без рекламы. Новый рекламный путь и коробка за пять реклам не добавляются.
- Offline streak учитывается устойчиво в пределах существующих правил; duplicate, timezone, перевод локальных часов и десять дней без сети не превращаются в безусловно подтверждённые посещения.
- Открытие выполняется только online через сохранённый original intent и server receipt.
- Double tap, ответ потерян после server commit и restart восстанавливают то же открытие и ту же награду без повторного списания/начисления.
- Pending animation не подтверждает баланс; результат и новый баланс приходят с сервера.
- При смене аккаунта чужой intent, receipt или награда не присваиваются новому пользователю.
- Приёмка сверяет UI и journal/ledger: ordinary+premium daily, offline duplicate, open/restart/replay/account switch. Исторический рисунок коробки или fake reply не является доказательством.

Источники: C:45–46,49,53,55; T09:20–25,38–42; T11:39.

## Play-покупка, подтверждение и восстановление

**Возможность.** Покупатель получает оплаченный товар один раз и может восстановить незавершённую обработку после потери ответа, перезапуска или выключения новых продаж.

**Проверяемое принятие:**

- Created, pending, confirmed, rejected и unknown различаются; PENDING и неподтверждённый token не выдаёт золото/premium.
- Идентичность purchase/операции сохраняется при reconnect/process death. Повтор callback не дублирует grant.
- Сервер проверяет binding к app account; recovery на другом UID не присваивает покупку.
- Query/recovery уже оплаченного и обработка refund работают при отключённой витрине новых продаж.
- ACK/consume соответствуют типу продукта и подтверждённому состоянию; после потери ответа повторяются безопасно. Локальный callback сам по себе не считается завершением.
- Недоступный Play/отсутствующий продукт показан честно; изолированная заглушка не выдаёт успешный платёж.
- Токены/order IDs/персональные данные отсутствуют в общих логах; evidence использует redacted IDs/hash.
- Настоящий sandbox на подходящем устройстве проверяет success, PENDING, cancel, loss между server grant и ACK, recovery после restart, другой аккаунт и refund после частичного использования. Fake Billing отдельно проверяет логику, но не подменяет Play.
- Реальные продажи и реальная покупка товара не входят в разрешение на тесты; sandbox/config readiness остаётся внешним условием полной приёмки.

Источники: C:47–49; T09:9,15,27–42; T10:13,25,29–31.

## Полные и частичные возвраты, legacy recovery и финансовые доказательства

**Возможность.** Возврат безопасно согласуется с grant независимо от порядка событий, количества купленного и частичного использования premium.

**Проверяемое принятие:**

- Постоянный token-level fence сохраняется во всех денежных маршрутах; boolean revoked не заменяет существующую защиту.
- RTDN является сигналом для текущей проверки/binding; неизвестное, pending, malformed или временно недоступное provider evidence не превращается в подтверждённую выдачу/списание.
- Ambiguous verification остаётся pending/repair. Нельзя одновременно снять fence и начислить товар без авторитетного основания.
- Partial multi-quantity refund учитывается кумулятивно: уже отозванное количество не отзывается повторно; повтор события не даёт второй ledger-effect.
- Wrong package/product/order/quantity/account отклоняются без чужого финансового эффекта.
- Сохраняются связи purchase→grant→used/remaining. Частично использованный premium отзывается только в пределах остатка своего grant.
- Known credited old ACKed settlement replay не выдаёт повторный grant. Unknown consumed token не получает новый grant без отдельного авторитетного proof/ограниченного repair.
- Legacy записи не представляются новыми verification receipts. Нужный repair ограничен, возобновляем и виден в audit; mass migration не подразумевается.
- Матрица: grant→refund, refund→grant, concurrent, reply lost после каждой TX, повтор RTDN, два устройства, другой UID, временный отказ Play, spent/part-used/unspent premium, multiple independent grants.
- При всех порядках balances/remaining неотрицательны, conservation сохраняется, на исходную операцию приходится один ledger-effect. Итог связывает purchase/premium/currency tests, HTTP/Firebase/rules и настоящий Play sandbox.
- Поддержка multi-quantity gold в коде не доказывает реальные магазинные настройки. Premium quantity>1 сейчас явный unsupported route; конкретная допустимая конфигурация SKU должна быть проверена, не молча предположена.

## Оплата всей подачи и наблюдение за проверками

**Возможность.** Создатель отправляет материал на Арену или в курс за одну понятную плату и наблюдает, как продукт проводит его через перевод и остальные проверки.

**Уже принято и проверяемо:**

- Базовая цена первоначальной полной подачи — **1000 ноликов за всю подачу целиком**. Перевод, тестирование, остальные этапы/проверяющие/вопросы/языки не создают самостоятельных доплат внутри этой подачи.
- Цена задаётся сервером и показывается согласованно с действующим тарифом; клиент не подменяет её.
- После подачи создатель видит прогресс всех этапов. Ему не требуется отдельно запускать, организовывать и оплачивать каждый этап.
- Независимость проверок, право допуска, причины отказа и история сохраняются. Решение не выбирает автоматически AI-only, людей либо смешанную схему.
- По последнему уточнению владельца каждая новая попытка подачи платная. При этом повтор сетевой отправки той же операции сам по себе не создаёт вторую оплату: новую подачу и transport retry нужно различать.
- Частичная повторная проверка стоит **100 ноликов × количество вопросов, требующих повторной проверки**. Для каждого такого вопроса в сумму включены весь цикл проверок и переводы. Доплат за отдельные этапы или языки нет; 1000 ноликов сверху не добавляются. Предел суммы автоматически не вводится.
- Действительно неизменённые и незатронутые части сохраняют результаты проверок; они не включаются в число вопросов для оплаты повторной проверки.
- Правки затронутого содержания требуют перепроверки всего затронутого, включая зависимые части; действительно неизменные проверки сохраняются. Новая версия требует нового допуска, уже выданные runs/events сохраняют frozen content.

**Открытая часть, которая пока не имеет полной AC:** механизм определения вопросов, требующих повторной проверки, с учётом зависимых изменений; момент резерва/списания; возврат при несостоявшейся услуге; получатель платы. Тариф уже принят и не требует повторного решения. Нерешённые правила нельзя вывести из старой бесплатной реализации или принять как техническую деталь. Платность новой попытки подачи не превращает сетевой retry в новую услугу. Все стадии перевода/тестирования включены, без поэтапных доплат.

## Серверные константы и отдельная синхронизация конфигураций

**Возможность.** Цены, лимиты, награды и другие изменяемые правила имеют одну серверную основу, а клиент получает отдельное согласованное обновление конфигурации.
