- (decision) Module boundary is NOT 'assessment' — it is the online-session machinery itself. Tournaments and the championship are coming and are online in the same sense; home quests and lessons stay offline. Theme tests and the final exam are the first two users of that machinery, not its purpose.
- (question) Arena's side of the line is unsettled — Tpov called it fifty-fifty, partially loaded, with the mechanic itself offline. Decide before the boundary hardens, because it determines whether the online module must also serve a partially-offline caller.
- (decision) Client never reads the session document; it speaks only to server calls, so redaction is enforced by function code rather than by Firestore rules.
- (decision) Question delivery order is image first, then text. Text arrival is the start signal for the visible timer, because text is fast and a player must not be able to claim a loading failure to buy time.
- (decision) A between-questions timeout bounds the gap from the player's answer reaching the server to the next question being issued and its timer started. Roughly a minute; exceeding it ends the session.
- (decision) On a session broken by timeout, every remaining question is scored as wrong. Chosen over not recording the sitting, because leaving it unrecorded lets players farm statistics by abandoning a bad run.
- (note) Precedent exists for the timeout policy: buildCodeAnswerOnAbort in RunnerLogic.kt already fills unanswered positions with the lowest digit for aborted lesson attempts.
- (decision) Client stores the assessment entity and its results, never its questions. Results are public information used for leaderboards and load like any other public content.
- (question) Where the visible timer starts versus where the server's deadline starts: if the deadline runs from issue, a slow connection eats the player's time; if it runs from the client's acknowledgement, latency is absorbed but the acknowledgement must itself be bounded. The between-questions timeout looks like the intended cap on that grace.
- (decision) RESOLVES the arena question: arena is offline play, not an online session. It runs on the existing offline runner and differs only in how content reaches the device — a provisioning policy, not a session protocol. The online machinery therefore never has to serve a half-offline caller.
- (note) Arena's provisioning policy, recorded for the boundary it implies and explicitly out of this spine's scope: up to ten random quests a day, extras purchasable one at a time, selection aware of difficulty — easy first, and a repeat of a quest whose easy questions were all answered correctly continues into hard ones, or hard can be bought directly at a much higher price.
- (decision) Content provisioning is its own concern, separate from both the offline runner and the online session machinery. Naming it now keeps arena's daily quota and purchase rules from being built inside either.
- (note) CONVERGENCE worth acting on: the predicate 'every easy question answered correctly' now governs three unrelated things — the next lesson unlocking in a course, admission to a theme test, and arena's hard-question unlock. Three callers is the argument that settles where it lives.
- (decision) ADOPTED, timer contract confirmed by Tpov: the server issues a question and starts its deadline from the client's acknowledgement that the text arrived, not from issue, so latency is not charged to the player. The between-questions timeout is the cap on that grace — no acknowledgement inside it and the session breaks.
- (decision) ADOPTED: the online session machinery lives in shared/core, not as a feature. It knows about sessions, questions, deadlines and scores, and nothing about exams or tournaments; the callers pass their parameters in. This keeps tournaments from depending on a module named after exams, and avoids the cross-feature import the project rules treat as debt.
- (decision) ADOPTED: the scoring functions — evaluateAnswer, computePercentScore, computeStars and the all-easy-correct predicate — move from lesson-runner's domain into core. Four callers now need them (offline lessons, theme tests, the final exam, arena's unlock) plus the JS mirror on the server; leaving them in lesson-runner would make it a dependency of everything that scores.
- (decision) ADOPTED: the same call that scores a sitting writes the admission record, in one transaction. No trigger, so there is never a window where the result exists and the admission does not.
- (decision) ADOPTED: the admission record lives under users/{uid}, so account switching re-subscribes it through the project's existing auth-scoped flow rule.
- (decision) ADOPTED: the certificate is signed with a server secret and verified only by the server, per ADR-0007 rule 2.
- (question) DEFERRED, to be revisited before the first certificate is a year old: verification depends on the server being alive, so certificates die with the domain. Packing the signed payload into the link itself would let the verification page survive as a static file. Roughly a day's work, not worth it now.
- (note) CONTRADICTION found while assembling the picture: the round table's proposal to keep final-exam questions out of Room does not work. Both assessments draw from the lessons' own questions — the theme test from the theme's, the final exam from the course's hard ones — and those payloads are synced to the device because lessons need them offline. By the time a player is admitted, they have played every lesson, so every answer is already local. Even the on-demand path (Quest.archived, content fetched per lesson) ends in the same place once every lesson has been played.
- (question) So the only real choices are: accept that answers are locally readable and lean on the timer, the 20-of-100 draw and anti-cheat telemetry; author a separate exam-only question bank that never syncs, doubling the authoring burden already at 2400 questions; or stop persisting payloads at all, which ends offline play. This is the last load-bearing hole in the design.
- (decision) THREAT MODEL stated plainly, per Tpov: the local answer cache is not the real boundary. A player who can automate reading answers out of Room can equally point a language model at the question, and that is unsolved industry-wide. The design does not pretend to defend against it.
- (decision) Mitigations against a model answering are content design, not architecture, and belong to quest generation rather than this spine: questions whose options are all plausible with only the taught one more likely, and short texts that keep the answer window small.
- (decision) RESOLVES the caching hole cheaply: a reserved pool. Selected hard questions — on the order of one per lesson — are marked reserved. They never appear in lesson play, never appear in a theme test, and are never published to the client, so they are not in Room at all. Only the final exam draws them, server-side.
- (decision) The reserved flag therefore gates client publication, not just selection: the publication pass excludes reserved questions from the client-readable tree while keeping them in the server-side draw index.
- (decision) Theme tests keep drawing from the ordinary, already-cached questions. Tpov considered reserving for them too and decided against it — the theme test is a rehearsal and its stake is stars, so the extra authoring is not earned there.
- (note) ARITHMETIC: a course of about sixty lessons yields about sixty reserved hard questions, which gives a twenty-question draw roughly three times its own size. That is a real draw rather than a fixed set, and it costs the author one extra question per lesson rather than a second bank.
- (question) Does the reserved pool need its own minimum, the way theme tests need 100 easy and 100 hard? At one per lesson the number falls out of the course's size, but a course with few long lessons could still land under the draw.
- (decision) Reserved pool is defined as a ratio, not a per-lesson count: one reserved question per twenty hard ones. At the certification minimum of 1200 hard per course that yields 60 reserved, three times the draw, and no new number has to be invented or checked.
- (question) Tpov proposed the server choosing reserved questions PER USER, so every question still reaches most players and answer statistics stay whole. The benefit is real; the cost is that content sync stops being a shared delta query by parent ids and cursor and becomes a per-user server-mediated feed, which is a rework of the working sync contract in ADR-0004.
- (note) Counter-proposal on file: keep reservation global and route exam answers into the same statistics pipeline that lesson answers already feed. Reserved questions then accumulate statistics from exam sittings instead of lesson plays, the author still learns which of them are badly written, and the sync contract is untouched.
- (question) Tpov proposed a ROTATING reserve: the same reserve for everyone, reshuffled by the server periodically, so statistics accumulate on every question eventually and players can still report a bad one. It solves both objections to a static global reserve without touching sync.
- (note) HOLE in plain rotation: a question rotated INTO reserve was already published and already sits in every device's Room. Rotation therefore cannot un-see it. For a veteran who has synced the course for a year, every question has been visible at some point, so the reserve is worth nothing to exactly the players who reach the final exam.
- (note) Counter-proposal: make rotation one-directional. Reserved means not yet released rather than temporarily hidden — questions graduate out of reserve into lessons permanently, gathering statistics and becoming correctable, while newly authored ones enter. The reserve stays genuinely unseen because it is always material never published. Cost: it drains if the author stops writing, so the certification check must read the current reserve size, not a historical one.
- (decision) SUPERSEDES both the static and the rotating reserve, on web research into how real certification programs solve this: EMBEDDED PRETEST ITEMS. A reserved question rides inside the live exam but is not scored. Statistics accumulate on it from exam sittings, it never enters lessons and is therefore never cached on a device, and once it meets standards it graduates to a scored item. This is standard practice — NCARB's ARE, ASWB, and typical certification exams ship roughly 20 unscored pretest questions alongside 150 scored ones.
- (decision) The exam therefore carries a few unscored questions on top of its 20 scored ones, and the player cannot tell which are which. That indistinguishability is what makes the statistics honest.
- (note) This retires the whole statistics objection without rotation: the reserve gathers data from exams rather than from lessons, so it never needs to be released to gather it. Rotation is no longer needed for statistics — only for exposure.
- (question) Exposure control is the separate known problem, and it is exactly the one unlimited retakes create. The industry ties retake rules to pool rotation so a repeat taker does not meet the same items, and uses randomesque or Sympson-Hetter selection to stop popular items being overexposed. Decide whether the draw is uniform random or exposure-controlled.
- (version) Research sources, checked 2026-08-29: ncarb.org on pre-test questions in the ARE, aswb.org on embedded pretesting and psychometric analysis, oasis-lms.com on item banking for certification bodies, vretta.com and assess.com on item exposure control.
- (decision) PEDAGOGY, which settles what the two difficulties are for: easy questions are theory and that is where learning happens, so they reveal the answer. Hard questions are multi-step problems built on that theory — knowing the theory makes them answerable, but they take thought and experience. Easy is enough to play and learn; hard is what assesses.
- (decision) RESOLVES what the server returns after scoring, with a third option neither side had proposed: not a bare percent and not per-question verdicts, but a recommendation of which lessons to revisit. A player learns that a topic was weak, never which item they failed, so retakes become study rather than search.
- (note) This single answer satisfies three earlier demands at once: the UX lead's per-theme breakdown, the PM's question about what a player learns between attempts, and the architect's warning that per-question feedback would collapse the pass mark.
- (decision) Hard-question answers are never published to the device, so scoring and the advice that comes with it are computed server-side and returned with the result. The client renders both.
- (note) resultAdvice already exists in lesson-runner's domain but is small: it counts weak digits and points at the lesson taught immediately before, within one theme. An exam spanning a theme or a whole course needs real attribution — questions carry lessonId, so failures can be traced to the lessons they came from and ranked. An upgrade of existing logic, not a new mechanism, and another caller for the move into core.
- (decision) The reserve and pretest-item machinery become optional rather than load-bearing: once hard answers never reach a device, an unseen question buys little, because seeing a question without its answer is the same position as having studied. Keep embedded pretest items as the way to gather statistics on new hard questions, drop the reserve as a security measure.
- (question) Tpov's catch, and it is load-bearing: if hard answers reach nobody and no player ever learns which item they failed, who catches a hard question that is simply wrong? A broken item silently costs everyone marks and cannot be contested by the person it robs.
- (decision) SUPERSEDES the previous line that pretest items were optional: they are now the quality gate, not a nicety. A newly authored hard question is unscored until it has enough data to show it behaves correctly, so a broken item never costs anyone a mark.
- (decision) The signature of a broken item is measurable and does not need anyone to see the answer: discrimination. If players who score well overall get an item wrong more often than players who score badly, the key is probably wrong. Positive discrimination means the item measures what the rest of the exam measures; negative means it does not.
- (note) Half of this already exists: functions/lesson-statistics.js already computes correctPercent per question and, in summarizeAnswerDistribution, which options were actually picked. A key that disagrees with what strong players overwhelmingly choose is the concrete detector. What is missing is correlating an item against the sitting's total score.
- (decision) When a broken item is found after it has been scored, affected sittings are rescored with the item removed. This is only possible because every sitting is persisted (CAP-21), and it is the answer to the fairness objection: the remedy is retroactive, not an apology.
- (decision) Players can flag a question as unclear during or right after a sitting without being told anything about correctness, giving a human signal alongside the statistical one.
- (note) ARITHMETIC for scale: at 20 questions and a 60 percent bar, one broken item costs five points, which only flips a result sitting between 60 and 65. A player at 99 percent does not fail on one bad item; two or three start to matter, and that is the range the pretest gate is sized to prevent.
- (decision) RESOLVES the exposure-control question: the draw is plain uniform random, chosen by the server, with no ranking, adaptive selection or exposure weighting in the first version.
- (decision) The pool is the hard questions the player COULD have encountered — those published to them in their version of the course — not the ones they demonstrably answered. No per-player filtering by answer history.
- (note) The 'could have encountered' qualifier is what ties the draw to the course version already decided in the spec: a question added after the player's version, or absent from it, is not drawn.
