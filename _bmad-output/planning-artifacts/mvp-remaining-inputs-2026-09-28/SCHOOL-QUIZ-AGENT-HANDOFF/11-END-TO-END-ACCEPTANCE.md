# ТЗ-11. Сквозная приёмка, устройства и перенос

Зависимость: завершены нужные code-срезы ТЗ-00–10. Результат — воспроизводимые доказательства работы и пакет для ручной проверки владельцем. **KMP и публичный выпуск — только после соответствующего отдельного разрешения.**

## 1. Зафиксировать кандидата

Записать HEAD/branch/dirty paths, версии Node/JDK/SDK, schema и server config/feature flags; SHA APK и сертификат. Разделить кодовый кандидат, реально работающий backend и установленный APK: три состояния должны быть сопоставимы. Сохранить базу/стенд перед изменением, не очищать для зелёного теста.

Прогнать серверные и Kotlin unit/integration, затронутые static, затем canonical `ciCheck` насколько применим на подготовленной среде. Недоступная задача — явный пробел, не PASS. Сохранить полные логи, counts/freshness/skips. Не складывать исторические прогоны.

## 2. Матрица расчётов и повторов

| Область | Обязательные случаи | Доказательство |
|---|---|---|
| Arena score/charges | EASY/HARD, неизвестная оценка, plasma skip, неправильное число вопросов | Authenticated receipt, фактический bank/version, журнал |
| Цена/автор | 1, 100, равный рейтинг, изменение после выдачи, дроби 80%, self-rating | Frozen ticket + payer/author/sink суммы |
| Резервы | 20 random/day, 5 selected, два tickets одного кошелька, cancel vs settle | Available/reserved, взаимоисключающий terminal |
| Повторы | response lost после debit/credit/open/refund; restart и resend | Тот же ID/receipt, никакого второго эффекта |
| Сезон | UTC quarter edge, 19/20 игроков, ничья, нет eligible, два finalize | Один winner/award либо no-award |
| Premium | expiry, overlapping grants, both regen ×2, возврат part-used | Неиспользованный остаток своего grant, другие сохранены |
| Турнир | 3 EASY, shared HARD, no agreement, один absent/оба, час, disconnect, byes, два third, <2 | Event/session times, bracket, conserved escrow/ledger |
| Большой отбор | 501/502 и доказанный больший размер, crash/lease/retry | Полный frozen cohort, deterministic versioned ranking, событие завершается |

Одно и то же серверное разрешение на двух устройствах должно иметь максимум один расчёт; два разных — оба могут законно завершиться при своих резервах. Не путать эти тесты.

## 3. Offline/update/account

- Подготовить запас онлайн → отключить сеть → начать разрешённый → restart/rotation/background → закончить → восстановить сеть → receipt/ledger.
- Запас исчерпан/нет подходящей версии → новый старт запрещён, старые данные не потеряны.
- Очередь **больше 50**, например 120 действий, доставляется без ручного многократного «пинка»; версии проверяются совместно с записью. Потеря ответа после commit не даёт повторного эффекта.
- A→B→A, один UID с новым epoch, stale cursor/late response и фоновые процессы, меняющие sync cursor. Никаких чужих writes/ACK/квитанций в новом аккаунте.
- Обновление поверх сохранённой непустой установки: сравнить schema/legacy table data до/после, firstInstallTime/auth и накопленные pending attempts. Ни uninstall, ни destructive migration, ни выдача legacy за новые confirmed results.

## 4. Полные пользовательские пути Maestro

1. Автор создаёт урок → независимые проверки → куратор → Арена → прохождение/оценка → авторская выплата → Турнир → Home. Статусы не подставляются административной фикстурой вместо шагов.
2. Курс остаётся в архиве → по его проверенным вопросам создаётся турнир → отбор → договорённость/матч → призы.
3. Обычный Home-smoke остаётся рабочим: этот старый путь не должен регрессировать после нового Arena runner.
4. Daily/premium box → открытие → response loss/restart/replay; gold premium и восстановление покупки; server journal.

Для setup тестовых ролей/малых временных окон допускается отдельная отмеченная fixture на **demo**, но она не подменяет доказательство проверяемого пользовательского перехода. Тестовые часы контролируются на серверном тестовом уровне, не через подделку клиентского результата.

Maestro: semantic selectors после осмотра настоящего UI, понятные bounded waits, уникальные output directories, `clearState: false`. Скриншот зелёного экрана + authoritative receipt/ledger, не одно без другого. Не удалять старые красные логи.

## 6. Ручная приёмка и выпуск

Передать владельцу APK, checksum/сертификат, commit, перечень включённых флагов, короткий сценарий ручной проверки и известные ограничения. Нельзя объявить ручную приёмку по своему Maestro-результату.

После явного согласия на перенос — проверить актуальное состояние KMP и новые пользовательские изменения, сохранить их, подготовить точечный merge проверенного состояния и повторить gates. Не считать нынешнюю KMP совпадающей с исторической базой.

Public release — ещё одно отдельное разрешение. Тогда сверить **актуальные** официальные требования Google Play к target API (в утверждённом плане указан 36), реально опубликованные versionCode, Billing/SKU/подпись, privacy/возрастную аудиторию/UGC/Families. Не считать историческую ссылку автоматической текущей юридической/магазинной проверкой. Не публиковать в ходе этого ТЗ по умолчанию.

Порядок совместимости: сервер → миграции/новый клиент → feature flags → сценарии → владелец → KMP → отдельно public. Старые оплаченные операции/возвраты продолжают обрабатываться при выключении новых продаж. Rollback не удаляет новую финансовую историю и не восстанавливает старую БД поверх подтверждённых денег.
