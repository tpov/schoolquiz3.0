# ТЗ-02. Достоверные баланс, резервы и незавершённые операции

Зависимость: ТЗ-01. Результат — данные, на которых безопасно строить подготовку/отмену в UI. Не реализовывать здесь магазин, runner или новый финансовый журнал.

## Подтверждённые пробелы

1. Серверный `profileResponse` уже отдаёт `reservedNolics`, `reservedLifePoints`, `reservedPlasmaPoints`. Клиентские `FirebaseProfileRemoteDataSource`, `UserProfile`, `RawUserStats` и Room не сохраняют полноценное представление резервов.
2. Серверные nolics — уже **доступный** остаток: резерв вычтен при выдаче. Нельзя ещё раз вычитать из него сумму локальных tickets.
3. Локальный список tickets — неполный/устаревающий, в том числе из-за других устройств. Даже последняя страница не доказывает суммарный резерв аккаунта.
4. `ensureCurrentProfile()` — upsert/регенерация, не read-only refresh. Старый stats refresh не защищён исходным epoch на всех внутренних записях. Вызов этих методов из новой кнопки не решает проблему.
5. Entry terminal-summary может скрывать сохранённое локальное решение SETTLE, которому после серверной отмены ещё нужно безопасно разрешить очередь. «Ticket CANCELLED» и «локальная доставка согласована и закрыта» — разные факты.

## Этап A — узкое наблюдение кошелька

Предпочтительный новый контракт: owner-bound `ArenaWalletObservation` и отдельный read-only reader. Имя предложено, такого API сейчас нет. Перед реализацией указать точные источники каждого поля и формат ответа/ошибки.

- Данные: UID, серверное время/время наблюдения, доступные nolics и lifePoints, их reserved-остатки; plasma — отдельными показателями только если реально отображается. Не смешивать очки жизни с числом слотов hearts.
- Источник — авторитетный серверный кошелёк, не сумма локальных tickets, не начальные constants/default stats. Чтение не создаёт профиль, не проводит регенерацию/покупку/резерв и не пишет ledger.
- Для изменяющегося со временем ресурса явно различить сохранённый сервером остаток и вычисленную проекцию на момент чтения. Нельзя назвать локальную проекцию новым подтверждённым начислением или гарантией достаточности средств.
- Существующие legitimately-legacy отсутствующие поля трактовать только по подтверждённому серверному контракту. Отсутствующий профиль, повреждённое число, неполный ответ → Unknown/NeedsRefresh, не финансовый ноль.
- Числа должны пройти строгую проверку целочисленности/диапазона; NaN, Infinity, отрицательные резервы, чужой UID и несовместимая версия отвергаются.
- Клиентский port принимает исходный `ArenaSessionStamp`. Проверять его до запроса, на точке отправки, перед local write и после возврата. Отмена корутины сохраняется.
- Если делается Room cache — отдельный typed snapshot с UID/временем/признаком свежести, следующая миграция после фактической схемы; старые строки получают Unknown, а не придуманные подтверждённые нули. Кэш не обязателен, если честно показывается отсутствие свежего общего баланса.
- Сетевое чтение вызывается явным событием/согласованным refresh; повтор не вызывает финансовую mutation. Никакого polling без ограничения и нового фонового sender.

## Этап B — необходимая информация для recovery

- Добавить к Entry-представлению минимальный typed признак сохранённого локального settlement/cancel intent, независимый от observed server terminal. Не раскрывать JSON/queue-body UI.
- CANCELLED + retained SETTLE должно предлагать `reconcileCancelledSettlement`, а не обычный ACK/удаление очереди. Только строгий proof и существующая exact-resolution TX закрывают эту доставку.
- SETTLED без принятой квитанции не превращается в «результат подтверждён»; восстановить существующую доставку/квитанцию штатным путём.
- Pending PREPARE показывать по исходному requestId. Связь заявки с ticket подтверждать только сохранённым точным requestId/серверным ответом. Если для такой связи недостаёт запроса, добавить узкий локальный lookup; не выбирать «последний ticket» и не создавать новый запрос.
- Не менять смысл terminal replay/cancel и финансовые guard-ы ТЗ-01. Отсутствие/повреждение банка не прячет возможность отменить известный корректный header.

## Приёмка

- Сценарий: доступно 100 → резерв 30 → доступно 70/резерв 30, UI не показывает 40. Отмена/settlement другого устройства обновляет общий резерв только по новому observation.
- Unknown, guest/default, missing, stale и zero различаются. Чужой/старый epoch не обновляет локальную строку/экран.
- Read-only endpoint проверен настоящими HTTP/rules-тестами: свой разрешён, чужой/unauth запрещён, кошелёк/ledger до и после идентичны.
- CANCELLED+retained SETTLE остаётся обнаруживаемым и разрешается exact-proof путём; повреждённый proof не удаляет очередь.
- Новый reader не обходит финансовое разрешение: достаточный показанный баланс не обещает успех будущего prepare.

Точный потолок **lifeCost** до выдачи сейчас не зафиксирован протоколом согласия: каталог даёт цену ноликов, а ticket — уже подтверждённый charge hold. В этом ТЗ не вводить скрытно новый тариф/авторезерв. Если выбранный UX требует отдельного ceiling зарядов, оформить конкретный контракт на review до реализации.
