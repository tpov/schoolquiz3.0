### Шаг 2. Кандидат C1+C3 и оснастка

Контекст: runId, account, ticketId, attemptId, lesson/version, frozen price, ratingId, candidate hashes. Старые квитанции не подтверждают новый запуск.

### Шаг 3. Первое полное прохождение, пункт 2б

SELECTED/HARD → подготовка → начало → сохранённый ответ → перезапуск → та же попытка → завершение → SETTLE → оценка 2 → RATE_LESSON.
Сохранённый аккаунт и прежний целевой урок — после проверки состояния, автора, банка, баланса. Привязка по lesson ID, изменённый title учесть только в selector.
Требуется одновременно: ticket/attempt/progress пережили рестарт; точная серверная settlement receipt; rating принят для того же owner/lesson/подтверждённой попытки; резерв/списание/author share согласованы с frozen ticket; нет повторных финансовых эффектов.
После ошибки за PREPARE сохранять контекст и продолжать исходную операцию, не готовить замену.

### Шаг 4. Остальная матрица Арены

- Потеря ответа после server commit, повтор прежнего ID.
- Настоящий offline из подготовленного запаса, restart и доставка.
- Rating Queued, restart, явная синхронизация.
- EASY/HARD, 20 random выдач в день, 5 одновременно подготовленных selected tickets.
- Неизменность цены после подготовки, cancel/settle race, позднее завершение отменённого ticket.
- Account A→B→A, поздние ответы, один ticket на двух устройствах.
- Аппаратный Back через системный dispatcher.
- Различная диагностика отсутствия сети и недоступного backend.

Недостающие роли/банки — отдельные demo-фикстуры с манифестом. Фикстуры готовят условия, приложение выполняет оцениваемые прохождения/рейтинги/выплаты.
Контролируемый demo-прокси обрывает ответ только после подтверждения upstream; реальный offline отключает сеть устройства при сохранённом управлении.
Продуктовые дефекты — небольшие отдельные commits с регрессией и повтором затронутых сценариев.

## 3. Остальные продуктовые ТЗ по порядку

- **TZ06A — допуск/цена.** Проверить восьмифайловый draft. Каталог/selected/random используют единую актуальную совокупность допущенных уроков. Лимиты чтения, никаких записей при ошибке, выданные tickets неизменны. Полные относящиеся Node/Firebase проверки, отдельный commit.
- **TZ06B — безопасное чтение.** Ограниченные серверные views статуса урока, истории, разрешённых причин отказа, author payouts. Author/curator permissions проверяет сервер; private collections закрыты.
- **TZ06C — автор/куратор.** Подключить views к authoring/review. Создание → независимые проверки → продвижение конкретного урока через UI. Новая версия требует нового допуска; ранее выданный content сохраняется.
- **TZ06D — экономика/сезон.** Price 1–100; одинаковый rating — одинаковая price; доли 80/20 без потери дробей; замена rating; запрет self-rating; кварталы UTC; однократные награды. Победитель сезона из полного проверенного состава, без усечения каталога.
- **TZ07A — большой отбор.** Версионированный расчёт по полному frozen cohort, сохранение прогресса; устранить бесконечное ожидание выше 501 принятой попытки после доказательства нового пути.
- **TZ07B/C — worker/турнир.** Ограниченный server-only запуск на demo. Сроки, crash recovery, одинаковые формы, технические исходы/пропуски, два третьих места, сохранение фонда при выплатах/возврате.
- **TZ08A–C — турнир в приложении.** Типизированные контракты, устойчивые операции; создание/поиск события, три отбора, посев, договорённость, матч, серверные итоги. Использовать шесть существующих callables; отсутствующий поиск — безопасное серверное постраничное чтение.
- **TZ09A–C — магазин/покупки.** Витрина, premium, ежедневные коробки, открытие, восстановление покупок. Gold prices — сервер, money prices — Play; ненастроенные товары явно недоступны.
- **TZ10A — возвраты.** Таблица purchase/grant/refund states; partial quantity, неоднозначная проверка, старые ACKed purchases, отзыв только неиспользованной части конкретного grant.
- **TZ10B — зависимости.** Отдельный commit; актуальный audit, минимальные совместимые обновления, clean install, текущие Node/HTTP/Firebase/rules проверки.

Решение владельца для TZ07A: исправлять численную погрешность будущих ещё не опубликованных расчётов. Сохранить LS-формулу и порядок tie-breakers. Компактная рациональная система не больше 3×3; округлять дроби ДО превращения в Number. Прототип с ранним Number доработать.
Фазы с сохранением: проверка входа → накопление статистики → решение → обработка игроков → публикация. У каждой cursor/revision, защита от stale worker, hashes. Calculation/rounding versions сервер фиксирует до начала. Опубликованные rankings/brackets неизменны; старый publisher не перезаписывает задание новой версии.

## 4. Контракты и обязательные проверки

Изменения интерфейсов только необходимые: versioned test run context и PASS/FAIL/NOT RUN/INTERRUPTED; typed paged author/curator views; tournament calculation version, full-input hash, private checkpoints; клиент не управляет worker/server time; добавочные purchase/grant/partial-refund связи при обратной совместимости старых операций.

На каждом срезе: behavioral tests затронутых контрактов, соответствующие server/Room/HTTP/rules проверки; анализ фактически изменённых production/test source sets.

Особые случаи:
- Деньги: цены 1 и 100; 5 оплат по 1 дают автору суммарно 4; повтор операции без второго эффекта.
- Сезон: 19/20 разных прошедших, смена квартала, tie, отсутствие победителя, конкурентный finalize.
- Турнир: 0/1/2/15/16/17 участников; 502 попытки; 502 разных игрока; 1503 попытки; 4096/4097 как test sizes, НЕ продуктовый лимит. Замеры времени, памяти, reads/writes, завершение после прерываний.
- Покупки: grant/refund оба порядка и одновременно; потеря ответа; частично использованный premium; независимые grants; другой account; restore при отключённых новых продажах.
- Устройства: update непустой установки, real offline, account switch, Play sandbox. Fake Billing отдельно от Play.

Одна тяжёлая сборка одновременно; сохранять подготовленное окружение и ограничения ресурсов. Последующее уточнение владельца: всё собирать/хранить на VPS, тестировать локальные физические телефоны, Android-эмулятор не использовать, диском занимается владелец.

## 5. Финальная приёмка и отчётность

Зафиксировать ОДИН финальный candidate: code, running backend, installed APK, schema, config и flags соответствуют друг другу. Свежие общие проверки включая `ciCheck` и матрица ТЗ-11:
1. Автор → независимые проверки → Арена → прохождение/оценка → выплата → Турнир → Home.
2. Архивный курс → турнир → отбор → договорённость/матч → призы.
3. Обычный Home smoke.
4. Коробки/premium → opening/purchase → потеря ответа → restart → restore.
5. Очередь 120 действий, update сохранённой установки, account isolation, два устройства.
6. Настоящие Play sandbox покупки/restore/refund.

После каждого среза: изменённые файлы, baseline/final commit, реально выполненные проверки и logs, ограничения и остаток. Исторические зелёные результаты не складывать с новой приёмкой. «Реализовано» без доказательств не является приёмкой.

Артефакты: актуальный state registry, `ACCEPTANCE.md`, `MANUAL-CHECK.md`, APK + checksum/certificate и ссылки на доказательства.
Полная приёмка требует всех обязательных проверок и ручного результата владельца. Открытые дефекты денег/потери данных/прав блокируют готовность. Недоступные Play/device проверки остаются незавершёнными.
