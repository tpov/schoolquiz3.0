# Разбор итогов эпика 1 — «Ошибки различимы, сеть детектируется»

## Что вышло

**Эпик.** «Ошибки различимы, сеть детектируется», истории 1.1–1.5 (`_bmad-output/planning-artifacts/epics-sync.md:165-326`). Задача: доменный тип неудачи обращения к серверу из пяти ветвей с объявленным решением по каждой, детектор связи, единственное место чтения исключения Firebase, таймаут на каждом callable, запрет уходить в сеть без сети и показ ветви вместо строки. Эпик объявлен фундаментом: движок эпика 2 принимает решение о повторе по этому типу, экран эпика 4 показывает по нему последнюю ошибку.

**Истории.** Все пять `done` в `sprint-status-sync.yaml:38-44`, `epic-1: done`, ретроспектива помечена `optional`.

**Доказательная база — что было.**

- Критерии приёмки: Given/When/Then по каждой истории в файле эпиков. Есть, и они необычно конкретны — с именами файлов, строк и утверждений.
- `epic-1-context.md` (43 строки) — цель, требования, решённые параметры, зависимости между историями.
- Журнал решений архитектуры: две записи, касающиеся эпика напрямую — `.memlog.md:23` (разведка: детектора сети нет, ноль совпадений `ConnectivityManager`/`NetworkMonitor`/`isOnline`, `FirebaseFunctions` без `setTimeout`) и `.memlog.md:98` (числа решены владельцем, среди них «таймаут callable 20 секунд»). Плюс AD-15 в спайне (`ARCHITECTURE-SPINE.md:149-153`).
- Коммиты — единственный эпик из разобранных, у которого они читаемы по существу: `a681181a` (2026-09-01 17:00, 242 файла, эпики 1–2 и часть 7 разом), `444ef718` (20:04, «review: three defects the tests were happy with»), `28bfa848` (20:26, «sync: the seventy-second wait ends everywhere, not in two places»).
- Код и тесты в дереве; прогон по модулям эпика (см. «Проверка поведением»).
- Образец формата — `epic-7-retro-2026-09-02.md`.

**Доказательная база — чего не было.**

- Привязки «история → коммит» нет. `a681181a` тематический и несёт сразу три эпика; ни один коммит не называет истории 1.1–1.5. Файлов историй нет — истории живут только в файле эпиков.
- Эпик собирался в **предыдущей сессии**. `shared/core/network` создан `a681181a` и с тех пор не менялся ни разу (`git log -- shared/core/network` даёт два коммита, второй — миграция KMP). `AndroidNetworkMonitor.kt` — тот же один коммит. Поэтому по историям 1.1 и 1.2 доказательство — только код и его тесты: ни промежуточных состояний, ни записей о выборах, ни следа в `deferred-work.md` (единственное упоминание эпика там — `:319`, «таймаут доехал до всех 19 вызовов»).
- Прошлого разбора этого эпика нет.
- Разделения диффа по эпикам нет: `platform/firebase/**`, `apps/android-next/**/di`, `android/feature/economy/presentation/**` правит и вторая сессия (монетизация). Где вывод зависит от их правок, я это называю.

## Находки

### Сверка с критериями

**1. Детектор связи не покрыт ни одним тестом.** AC 1.2 называет пять утверждений поимённо: портал точки доступа (`INTERNET` без `VALIDATED`) → `false`; `getSystemService(...) == null` → `true` «отдельным тестом»; первое значение приходит до колбэка и равно `isOnline()`; `onLost` по Wi-Fi при живой мобильной → `true`; `unregisterNetworkCallback` вызван ровно один раз, «тест считает вызовы на фейке». В дереве: `platform/android-services/src/test/**` содержит три каталога — `economy`, `push`, `sync`; каталога `network` нет, файла с упоминанием `AndroidNetworkMonitor` нет ни одного (`grep -rl NetworkMonitor` по `platform android apps shared` даёт 12 файлов, среди них ни одного теста этого класса). Сама реализация выглядит правильной — `AndroidNetworkMonitor.kt:65` отдаёт `true` при `connectivity == null`, `:28-63` шлёт текущее значение до `registerNetworkCallback` и держит множество валидированных сетей, — но это прочтение кода, а не проверка. Robolectric в проекте есть (`gradle/libs.versions.toml:80`, 4.11.1), препятствия к тесту нет. Решение: **чинить сейчас**.

**2. Историй 1.4 и 1.5 не покрывает ни один тест, и написать требуемый нельзя по форме классов.** AC 1.4 требует «JVM-тест источника данных с фейковым `NetworkMonitor` и фейковым транспортом», в котором «счётчик вызовов `getHttpsCallable` на фейке равен нулю». `FirebaseEconomyRemoteDataSource.kt:17-19` принимает конкретный `FirebaseFunctions`, а не порт, — фейкового транспорта в такой конструктор не подставить, и в `platform/firebase/src/test/**/economy/` лежат только `EconomyConstantsResponseParsingTest` и `PurchaseVerificationMappingTest` (обе — про разбор ответа). То же у `FirebaseMutationTransport.kt:23-25` и у `FirebasePurchaseVerifier.kt:30-33`: три класса несут предпроверку связи, ни один не проверен. AC 1.5 требует JVM-тест `DefaultShopComponent`; в `android/feature/economy/presentation/src/test/**` два файла (`DefaultShopComponentCancelListingTest`, `NicknameShopStateTest`), `grep NoNetwork` по ним пуст. Контраст рядом и он же образец: та же предпроверка, поднятая в use case над границей SDK, проверяется без труда — `BuyGoldPackUseCase.kt:39-40` и `BuyGoldPackUseCaseTest.kt:65-72` (`offline refuses with NoNetwork and never opens the store`), файлы параллельной сессии. Решение: **чинить сейчас** — перенести предпроверку выше границы SDK либо завести порт вызова.

**3. Предпроверка связи доехала до одного синхронного действия из четырёх.** AD-3 и AC 1.4 называют четыре: покупка заряда, покупка и смена ника, покупка лота, покупка логотипа; технический контекст истории прямо перечисляет `FirebaseNicknameRemoteDataSource.kt:76`, `FirebaseLogoRemoteDataSource.kt:60`, `FirebaseGiftBoxRemoteDataSource.kt:14` как места, куда «проброс `networkMonitor` делается здесь и единственный раз». В дереве `NetworkMonitor` есть только в `FirebaseEconomyRemoteDataSource.kt:19` (покупка по каталогу и `unlockLesson`). Конструкторы `FirebaseNicknameRemoteDataSource.kt:23-24`, `FirebaseLogoRemoteDataSource.kt:20-21`, `FirebaseGiftBoxRemoteDataSource.kt:9-10` принимают только `FirebaseFunctions`. Последствие видно целиком: `DefaultShopComponent.kt:333-341` (`claim`) и `:359-367` (`buyLogo`) ставят `processingNickname` до вызова и снимают после, а `NoirNicknameMarket.kt:170,:220,:401,:654,:685,:759` рисует по нему `busy`. Без сети предпроверки нет, значит кнопка занята до истечения таймаута `CallableErrors.kt:25` — тридцать секунд вместо семидесяти, но всё ещё спиннер, который FR28 запрещает. Решение: **чинить сейчас** для ника и логотипа. Гифт-бокс отношу к монетизации и в счёт эпика не беру.

**4. Решение: **чинить сейчас** — одна строка в `FirebaseModule.kt` на каждый порт (`.namingFailures()` уже есть и применён к десяти другим).

**5. `ShopMessage.NoConnection` не существует; ветвь «нет связи» доезжает до экрана строкой.** AC 1.5 требует трёх вещей дословно: `state.message` равно `ShopMessage.NoConnection` «отдельному значению `sealed interface ShopMessage`, не `Failure(detail)`» (`epics-sync.md:299`); `NoConnection` — «`data object` без полей: сырая строка платформы в этой ветви наверх не поднимается физически, а не по договорённости» (`:300`); экран показывает «строковый ресурс ветви „нет связи“ из `strings.xml`, отличный от ресурса, которым отображается `Failure`» (`:309`).
