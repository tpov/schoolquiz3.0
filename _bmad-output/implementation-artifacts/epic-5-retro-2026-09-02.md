### Aggregate views

**Spec-to-implementation reconciliation**
1. *Operation name for lesson unlock diverges from Story 5.3.* AC says `operation = "lesson.UNLOCK"`, `entity_ref = "lesson.LESSON:<lessonId>"`, handler in the lesson feature's Koin module. Code: `shared/core/outbox/.../OutboxOperations.kt:20` `UNLOCK_LESSON = "UNLOCK_LESSON"` — the only operation without a feature prefix; server registry key is the same bare literal. `OutboxOperationsRegistryTest` documents why the bare name was kept (identifier `UNLOCK_LESSON` is already bound to `"lesson"` in `functions/index.js`). Disposition: **spec reconciliation + fix** — rename to `lesson_runner.UNLOCK_LESSON` on both sides (no live installs) or reconcile the story to the bare name with the reason; either way the story text and code must agree. Logged in `deferred-work.md`.
2. *Story 5.6 "already sold" mark went beyond its AC.* AC: the lot row draws the "уже продан" mark. Built: the row also disabled the "Снять" button on `REFUSED` (`NoirNicknameMarket.kt`, former lines 480/841), and quarantined rows were kept beside new intents. Combined with `OutboxDao.observeByEntityRef` returning the newest row, a re-listed name kept its button dead forever (reviewer, journal `wf_dff6ed1e-9cf`, finding 4). Disposition: **fixed in this session** — new intent withdraws the quarantined row (`ListingCancelQueue.kt`, `QuestRepositoryImpl.queueShelfChange`), re-listing forgets the refusal (`NicknameRepositoryImpl.listForSale`, `LogoRepositoryImpl.listForSale`), button no longer locks; AD-28/AD-2 refinement recorded in the architecture memlog and ADR-0004. Tests: `ListingCancelQueueTest` (26 cases), `QuestRepositoryImplShelfChangeTest` (27 cases in module).
3. *Story 5.5 replay criterion was not met by the server as first built.* AC: review record created once and reputation credited once, "including `addReviewerReputation` outside the transaction". Built: `reviewId` included `now`, so a replay after a stale reservation (instance died between `batch.commit()` and key completion) would create a second record (server agent's own Open Question #1; reviewer confirmed, finding 3). Disposition: **fixed in this session** — receiver passes `mutationId` to handlers; `reviewIdForMutation` derives `m_<mutationId>`; body returns the saved-equivalent result before `canSubmit` when the record exists (`functions/index.js`; source guard `review-replay-idempotency` in `functions/deferred-actions.test.js`).
4. *Story 5.1 module boundary holds.* `grep -ciE "nolics|developerLevel|listing|assignment" functions/mutation-queue.js` → 0, as the AC requires.
